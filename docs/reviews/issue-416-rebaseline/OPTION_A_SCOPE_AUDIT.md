## Why simply stripping VAP1 is unsafe

Current source grants ordinary runtime SQL session INSERT and MFA factor/assurance UPDATE (`packages/database/scripts/mfa-runtime-privileges.mjs:1-34,142-207`). Staff token and MFA policy then trust those rows (`staff-session-context.ts:53-73`, `mfa/mfa-assurance-policy.ts:73-137`). Meanwhile `staff_management_set_role/status/location_access` are SECURITY DEFINER functions accepting actor membership UUID, with runtime EXECUTE restored by `staff-management-runtime-privileges.mjs:18-32`. These are conditional T5 trust-boundary defects, not proof that HTTP requests without SQL access succeed. Neither a new reset table nor a NestJS role check fixes fabricated upstream issuer authority under T5.

## Evidence needed before selecting a smaller implementation

Run isolated PG17 as the actual ordinary runtime role, including all column-level/PUBLIC/inherited/default ACL, role graph, function overloads and re-provisioning twice. Attempt synthetic session and MFA forgery, privileged actor ID spoofing, quotas and actual accepted API operations; confirm whether constraints or triggers prevent end-to-end acceptance. Inventory each active writer's SQL requirements before grant removal. Reconcile with accepted DEC-072/078/080/081, source freshness and the Owner's threat model. **No historical W9 execution and no production mutations.**

# Candidate Option B — minimal secure Company Admin Staff Password Reset

**PROPOSED ONLY, not approved or implemented.** Exact baseline: `db85db57fc5c3913a22d34ab5d9ef77269756301`. Never enable this design until the upstream authority and privileged SQL boundary below is independently proven. This is not a claim that replacing v9 with ordinary Prisma transactions is T5-safe.

## Non-negotiable authority and threat boundary

**T1–T4:** Authenticate the actual submitted `vsa1` bearer, not client-supplied actor UUID; resolve currently ACTIVE global User, exact StaffAuthSession and membership; check same ACTIVE Organization, ORG_ADMIN, current entitlement, same-session MFA within five minutes; target is ACTIVE and has exactly one OrganizationMembership globally across all statuses, eligible LOCATION_MANAGER/VALET_SUPERVISOR/VALET_EMPLOYEE, not actor/platform/admin; many Location grants in the sole Organization remain valid. Repeat these checks under SQL locks during issue. Treat frontend state as display, never proof. Keep the approved Admin-trust model (issuer may personally redeem link).

**T5:** The current ordinary runtime SQL role can, according to its source provisioner, create or update Staff session and MFA authority (`packages/database/scripts/mfa-runtime-privileges.mjs:1-34,142-207`). Therefore a narrow reset-specific SQL function that trusts existing session/MFA rows still allows a SQL caller to forge its issuer. To genuinely preserve T5, **either**: (i) close all upstream security-critical session/refresh/MFA/role/management credential-provenance paths with independently reviewed restricted writers, **or** (ii) implement a separate reset-specific trust island: separately bootstrapped administrator credential and Org enrollment, private immutable issuer epochs/revocation, a ceremony authenticated independently of mutable legacy session/MFA state, and a purpose-specific app signer inaccessible to ordinary SQL. This second option introduces new operational recovery and MFA enrollment burden and **requires explicit Owner approval**. No public reset can go live on a stored PHC, SQL-readable hash, caller ID or MFA timestamp alone.

An independent issuer trust root also requires proof that ordinary SQL cannot poison the reset decision via target `users` status, memberships, Organization status or commercial entitlement. Merely isolating the Admin credential while trusting all mutable legacy authorization facts does not establish T5. The minimum trust island needs **verified initial human/organization enrollment**, an independently attested Admin-to-Org binding, a reset-specific authenticator/factor **not derived from forgeable `vsa1` and legacy MFA DB rows**, controlled factor loss/recovery, signed private issuer/Org revocation epochs and trusted authoritative updates when role or Org changes. Only an independently authorized enroll/revoke principal may change that root, not normal application runtime SQL. The legacy SQL actor-UUID definers must be effectively retired, or the trust-island proof must reject all consequences of their writes; inspect external P02 entitlement writers before choosing. Recheck actual current CA/target/membership/entitlement for business rules but never treat mutable rows as the only proof of authority. This is operationally significant and may defeat Option B's simplicity advantage.

**T6/T7:** A compromised signer/app host or migration owner defeats its own trust root. Contain keys, isolate owner roles, maintain off-DB operator evidence, use key epochs/retirement and safe fallback OFF; do not promise T6/T7 resistance from an ordinary symmetric HMAC.

## Exact private persistence and SQL authority

Purpose-specific private relation (or reuse verified dormant migration `20261113012600_issue416_private_reset_credentials` where compatible): **`UNIQUE (organization_id, operation_id)`** as in existing source, plus `request_digest`, issuer User/membership/session linkage, target User/membership, `generation` unique per target, `token_verifier` unique, `created_at`, `expires_at`, `consumed_at`, `revoked_at`, `receipt_digest` and a unique-current-token invariant. DB-controlled issuance clock and FK/CHECK constraints enforce state, no secret-bearing public SELECT. **TTL design blocker to resolve before acceptance:** source migration126 calculates timestamps at INSERT, not at actual COMMIT; a transaction delayed between INSERT and COMMIT would deliver less than 15 minutes of validity after commit. The accepted “exactly 15 minutes after committed issuance” must be defined with an enforceable publication/commit-time ABI and delayed-COMMIT test, not silently approximated by INSERT time or longer TTL. Do not enable until resolved with Owner approval.

Generate 32 CSPRNG bytes as canonical `vspr1.` plus 43 unpadded base64url (`apps/api/src/modules/auth/staff-password-reset-credential.ts:6-19`). Store purpose-separated SHA256 credential verifier, not raw reset token. Credential quota uses a **different purpose-specific HMAC of exact canonical raw bearer**; HMAC and SHA256 verifiers must never be directly equated. Copy link over HTTPS `/staff/reset-password#reset=` only after certain issue COMMIT. Fragment is scrubbed before any subsequent navigation; no token in query, browser storage, analytics, trace, HTTP/SQL logs or telemetry. `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, CSP and no auto-delivery.

Use a narrowly scoped private SQL writer owned by separate NOLOGIN/NOINHERIT role with fixed `search_path`, restricted EXECUTE, no dynamic SQL, no generic MAC oracle. The trusted application ceremony validates **actual reset-specific credential/factor possession independently of legacy bearer/MFA rows** plus actual submitted `vsa1` for ordinary session lineage, binds purpose, exact operation request digest, immutable enrolled Admin/Org authority, actor/target/tenant, session, key epoch and a one-use challenge to a protected SQL transaction. Pin challenge to actual same-lease backend PID and full transaction ID (`pg_current_xact_id()`), or formally demonstrate a comparably strong one-use cross-backend and replay-resistant binding; restrict MAC frame to exact reset purpose, fixed typed fields and key epoch. The SQL writer revalidates all current actor, target, entitlement, revocation and token constraints under deterministic locks. A separate DB writer principal/process is only equivalent if stealing ordinary runtime SQL credentials does **not** grant or reconstruct that writer's authority. Never leave old definer actor-UUID functions callable to bypass the issuer. Test copied proof on a foreign backend, late/duplicate challenges and key-epoch rollover.

## R02 issue quotas, independent before domain COMMIT

Rolling 15-minute private immutable quota events/reservations, serialized across keys under READ COMMITTED: target User **3**, issuer User **20**, Organization **100**, trusted server-resolved client IP **30**. A real operation-bound reservation is independently committed before protected issuance writer; rollback of reset row/audit does not erase attempt. Exact same `operationId` + payload digest replay reuses prior operation without fresh budget; changed-payload replay is denied. Reject fabricated COUNTED/IGNORED events and SQL-only quota discounts. Return bounded `429 Retry-After` for exhausted quota; fail closed `503` on unavailable quota.

**R02 reservation state machine:** before spending budget, read the exact operation identity and canonical request digest in an authoritative lease; distinguish an existing `PENDING` separately committed reservation, a definitively `COUNTED` committed issuance, authorized `IGNORED` nonchargeable disposition, and unresolved **UNKNOWN COMMIT**. A same-operation replay does not create a fresh reservation only after exact authenticated binding; unresolved outcomes must remain conservative and charged until an immutable domain receipt proves a specific finalization, never caller-asserted COUNTED/IGNORED. A protected finalizer must bind the original quota event to the domain transaction/receipt and cannot discount a business-writer rollback attempt. R03, unlike R02 idempotent issue, counts each submitted request's independently committed IP and canonical credential attempt; no rollback refund.

Issue COMMIT atomically advances latest generation, stores one private token verifier, invalidates predecessors, and inserts immutable issuer/target account-security audit and exact operation receipt. Permit 200 `LINK_ISSUED` only after certain acknowledged matching COMMIT. Do not redisclose secret if acknowledgement is lost.

## R03 redeem quotas and atomic password rotation

Before Origin, Content-Type or JSON schema parsing, independently COMMIT trusted-IP attempt **30 per 15m**, including malformed requests. Then if canonical reset bearer is present, independently COMMIT token-keyed keyed-HMAC attempt **5 per 15m**, including invalid/expired/consumed. Both counters resist cross-transaction rollback, two-backend contention and forged status. A token SHA256 is never used as a substitute for quota HMAC.

Validate password policy, Argon2id derive new PHC in app, then a single SQL transaction locks exact token/target User and all affected session/refresh/Push rows in a documented consistent rank. Recheck token ACTIVE, unexpired, exact generation, **current issuer Company Admin/Organization/entitlement and eligible target state**, and trusted issuer lineage. Atomically update `users.password_hash`, consume token, revoke sibling reset links and every target StaffAuthSession; ensure **all** dependent RefreshCredentials become unusable through strict live-session lookup and legal terminalization of active generations, with no assumption of a nonexistent `refresh.revoked_at` or illegal `consumed_at` rewrite for expired credentials. Disable active Push registrations and clear provider tokens; append immutable anonymous account-security audit and exact receipt. `User.status`, MFA factors/recovery codes, Org/location grants, Tasks/Shifts/Custody unchanged. Do not create a session or new MFA assurance. Test every refresh generation under a real mounted refresh call, including concurrent login/rotate.

## Lost COMMIT and error semantics

Operation ID + immutable request digest + exact trusted receipt/lineage permit bounded authorized status readback after an unknown acknowledgement. An unknown response is **not** a rollback. Never automatically repeat issuance/redemption, reveal a raw bearer from receipt, or use same-user/same-millisecond unrelated receipt as proof. R02 replay returns linkless `LINK_UNAVAILABLE`, R03 token replay generic denial. HTTP status 200 only after known required outcome, safe generic invalid-token errors, bounded 429 and fail-closed 503. Do not leak whether employee exists.

**R03 anonymous recovery is not a public receipt lookup:** use a fresh private trusted read lease with exact server-generated operation ID, raw-bearer-derived token SHA selector, reset row/generation, purpose-bound signed payload and challenge, committed `ANONYMOUS` audit plus immutable receipt digest. Prove the original transaction and domain mutation; do not treat a consumed token or an unrelated receipt as proof of this request. An outside caller cannot supply only an operation ID to query private receipt state or to obtain success. Current `issue416-r03-atomic-closure.ts` is a pre-COMMIT predicate, not this readback.

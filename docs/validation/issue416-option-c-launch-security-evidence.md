## S04 anti-abuse — source proof, not yet independent mounted exploit

`packages/database/scripts/provision-runtime-role.mjs:211-240` GRANTs runtime `SELECT, INSERT` and `UPDATE(state,group_key_hash)` on `public.anti_abuse_events`; `anti-abuse.service.ts` counts only PENDING/COUNTED, with necessary separate Staff/MFA/Guest legitimate IGNORED outcomes. SQL principal with such privileges can discount existing matching counters or poison group accounting, but the HMAC secret is not deducible solely from a stored key hash. No W56 actual-role HTTP acceptance chain was completed; S04 remains a **source-confirmed security weakness, live exploitability and priority require dedicated PG17 verification**. Blind `REVOKE` or deleting IGNORED settlement would break Staff Auth and Guest behavior; first introduce a trusted, immutable purpose-bound counter and finalizer.

## Explicit unmet launch gates / Owner architecture decision

**Material decision:** protecting S01/S02/S03 against ordinary SQL role compromise while preserving live login/MFA/Management needs a separate, independently provisioned and rotated **security-command writer DB principal and restricted connection-pool boundary** (or an equivalently demonstrable protected cryptographic command boundary). This is a new credential/trust architecture; Option C does not silently authorize it. The narrow Staff-only `STAFF_AUTH_WRITER_DATABASE_URL` draft is in `docs/reviews/issue-416-s01-option-c/STAFF_AUTH_WRITER_ROLE_DESIGN.md`, and MFA integration/role cutover in `docs/reviews/issue-416-s02-mfa-origin-gate.md`. Neither is implemented. Any selected design must additionally prevent ordinary runtime SQL EXECUTE on actor-UUID legacy management and onboarding/custody-related overloads, update provisioners/verifiers (including twice-reprovision), preserve transactional MFA/admin activity and anti-abuse, and pass real deny/allow and concurrency suites. Avoid turning this into universal VAP1.

**Separate first-customer operational blocker:** forgotten ACTIVE Staff passwords currently have no live approved recovery route. `docs/security/issue416-customer-account-recovery-policy.md` is a policy proposal, not an implemented customer tool. Customer identity enrollment, two independent support operators, secret delivery, security event receipt and a tested purpose-only recovery workflow need separate operational authorization before onboarding real customers. No production SQL password edits or enabling unfinished Reset.

## Domain and security implementation

### #292: optional historical marker, later REQUIRED policy

Forward-only migrations `20261015008200_issue_215_condition_photo_policy_recovery` and `20261015008300_issue_215_condition_photo_policy_recovery_finish` (242 and 253 SQL lines) add a narrowly scoped helper and replace the existing P1 authorized upload SQL signatures without editing applied migrations. Upload after a historical completed Condition marker is eligible only while the session is still `CHECKING_IN` and **current effective policy** requires new photos. `FOR UPDATE` session lock and `FOR SHARE` policy locks serialize policy changes with admission; actor/membership/Location scope and original operation/lease limits remain authoritative. Historical marker, custody version and Task/Dispatch/Key Custody behavior remain unchanged. An untrusted metadata row never becomes verified evidence.

### #286: PENDING to REJECTED

Conservatively deferred pending explicit owner-reviewed permanent post-T1 error classification. Transient storage failures, readback outage and unknown PUT outcomes remain durable PENDING with a safe diagnostic and can expire/reconcile through fenced maintenance. None is automatically classified as object absence. Do not claim REJECTED behavior implemented.

### #293: exact cancellation bearer race

Cancellation POST and cancellation-status GET now forward the bearer to a required `StaffSessionContextResolver`. Inside the cancellation transaction, after existing Location lifecycle locking, the exact current session hash/ID/creation time, revocation and expiry are rechecked under the same Staff user/session locking discipline as other sensitive operations. Recheck also happens just before return/commit; a stale logout/refresh/expiry loses and rolls back the custody mutation and audit. Existing Version CAS, authorization, cancellation idempotence and append-only audit are preserved.

### P2/P3 baseline protection

Authenticated server-mediated actual JPEG bytes, canonicalization, EXIF stripping, immutable private object attempt versions and readback SHA-256 remain the only way to create verified evidence. P3 trusted policy receipt re-reads the exact selected private object/version. Native `VERIFIED` presentation and final Check-In authorization must be based on server current discovery and latest policy, never on a client URI, 202, pending journal or old Condition marker. The P3 qualification gate is intentionally `NODE_ENV=test`; development/production positive qualification requires separate approved provider/attestation decisions. No local flag is production authorization.

### P4 Portable and Native

`@valet/employee-client` provides typed scope/auth/capture-revision/request-sequence fencing and status/discovery/explicit reconcile without automatic mutation replay. Native uses an authenticated `FormData` carrying an actual Expo `File` JPEG; the still camera follows the existing QR visual pattern and exposes permission, preview, retake, confirmation, progress, verified/current server discovery, unknown and error controls in the Condition photo area. Private cache/source URI checks, partial-copy cleanup, failed-delete retry, startup cleanup and blur/background/account switch purging close known leakage windows. The optional no-photo Continue remains fast and server policy remains authoritative. An ambiguously dispatched POST followed by 404 remains UNKNOWN by design; the server cannot prove the earlier POST stopped merely from the 404.

### P5 conservative maintenance

Forward-only migrations `20261015008400_issue_215_p5_photo_maintenance_claims` and `20261015008500_issue_215_p5_photo_integrity_system` (158 and 94 SQL lines) add bounded expiry/ABANDONED inspection claims with database-time lease owner/generation and defensive refusal of SELECTED/verified evidence, legacy `vehicle_photos` key aliases, active leases and same-session incidents. Maintenance restricted role has `SECURITY DEFINER` allowlisted RPCs, no generic direct private table SELECT/UPDATE or image finalization; deferred read-only coherence/audit trigger functions use fixed safe search paths and preserve PUBLIC revoke. Worker starts only under explicit enabled flag and dedicated database URL, checks current/session role identity, and uses bounded SIGTERM-safe sweeps and numeric-only logs. It may perform exact private version READ for integrity, and a proven digest/version mismatch can atomically record AVAILABLE→UNAVAILABLE plus one SYSTEM audit. `strongVersionedReadProved=false` prevents uncertain provider absence from being declared missing.

The shipping worker supplies a `noDeletionStorage` whose list/delete methods throw and never passes `enableAbandonedDeletion`. The dormant exact-version cleanup adapter is present for future approved work but is unreachable from the runtime worker; delete-enabled configuration is rejected at startup. **Object deletion remains NO-GO** because a reference or Incident hold may be registered after a DB claim and before an external DELETE, and legal/backup/provider conditions have not been approved.

## Proposed path for review, NOT an enabled grant

1. Caller starts a **READ COMMITTED** `inPostgresTransaction`, using the *currently resolved* Staff bearer context; do not use an arbitrary resolved Dashboard navigation/scope hint as authority.
2. Reuse the **current Live-history location** prerequisite (`live-history-read-authorization.ts`): SHARED `staff-user-security` advisory, current exact Staff session `FOR SHARE`, CA current MFA/active factor `FOR SHARE`, SHARED `staff-management-org` advisory, current Dashboard commercial entitlement, active Organization, Location, membership and LM exact Location-grant `FOR SHARE`. Existing Staff security/grant revocation writers use conflicting locks. **A prerequisite is not an image permission.**
3. Derive authoritative Organization **server-side** from the validated Location scope; never accept a client Organization ID as authority. Recheck current Location against that scope, persisted membership role and status `FOR SHARE`, apply the owner-approved photo-only role policy, and require the exact `valet_sessions` row where `id + organization_id + location_id` all match `FOR SHARE`. One Vehicle may have multiple ValetSessions; a Vehicle identifier is never sufficient.
4. **W4 separate evidence layer:** select at most 10 qualified `CHECK_IN_CONDITION` photos from the same exact Session, with durable verification + selected operation/attempt + current availability `AVAILABLE`. Client photo IDs cannot stand alone as permission. On each bytes request require *fresh* staff VIEW auth, exact photo binding, bounded private `readExact`, object-version/digest/byte-length verification and recheck access+availability before responding. Do not expose object key/hash/version/provider/bucket or public/signed URLs in DTOs. Return `no-store` and uniform non-disclosing failures.

## Locks and open revocation proof

All SQL projection and evidence checks that rely on this gate belong in **the same caller-owned READ COMMITTED transaction** holding the above shared locks until COMMIT. No provider/network/S3 fetch under that transaction. Because released locks cannot fence mid-fetch/final HTTP-byte streaming, successful manifest auth is **not** a reusable read token. Bytes must reauthorize in a *new* bounded transaction **after S3 fetch**, with independently verified current evidence. **Do not COMMIT before HTTP enqueue:** the final transaction's SHARED locks must remain held until the synchronous `res.end(verifiedBytes)` call has enqueued the response. Do not await network or object I/O while those DB locks are held; do not claim the lock prevents a client from physically receiving already-enqueued bytes after revocation. The exact guarantee around concurrent revoke/logout/role or grant mutation, `AVAILABLE -> UNAVAILABLE`, and response enqueue remains a **required design+Postgres concurrency proof** prior to approval. DB admin/raw privileged writes that bypass canonical advisory lock protocol remain a documented separate threat boundary.

**Owner gates:** accept target CA/LM/Supervisor role matrix, CA MFA freshness and LM rule, completed/inactive session policy, private byte transport/revocation timing and audit/retention/provider safeguards. Until accepted, production must **deny** even legitimate Dashboard/LIVE readers and report that the feature is not yet authorized rather than pretending images exist.

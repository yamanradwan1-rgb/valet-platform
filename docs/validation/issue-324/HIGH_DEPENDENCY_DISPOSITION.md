## Boundary assessment and safe next decisions

1. **Prisma config merge — local operator/developer input.** The confirmed vulnerable sink is within Prisma's CLI config loader, which is invoked by tooling such as `prisma validate` and migration commands. VAYLET's config is JavaScript but fixed in Git; remote `c12` config fetching is explicitly disabled by the consumer. No untrusted graph input was traced through the product service to `deepmerge`. Preserve trusted-only config and prohibit unreviewed dynamic object merging. Candidate fix: a **targeted** override to `deepmerge-ts >=8.0.0` only after verifying Prisma's merger contract and its config/migration behavior in an isolated environment. Although the `deepmerge` named export still exists, v8 is a major and could alter merge semantics. A broad forced Prisma downgrade or untested v8 override is not warranted by current proof.
2. **MySQL2 auth — rogue database endpoint precondition.** The claimed leak requires actual `mysql2` network connection with a password and a malicious authentication-switching MySQL peer. The selected PostgreSQL provider and URL guard defeat that path in the examined VAYLET migration setup. Preserve PostgreSQL-only policy; do not allow a plaintext MySQL DSN via tooling or environment. Candidate fix: a **scoped** Prisma-dependency override to `mysql2@3.23.1` (addresses the High and related Moderate advisory) if Prisma supports its 3.x driver behavior; verify CLI boot, `prisma validate`, generate/migrate on disposable PostgreSQL and frozen lock resolution. Otherwise wait for Prisma's own compatible pin. Upgrade is not needed to prove a nonexistent MySQL runtime request path, but remains an unresolved advisory until the lock changes.
3. **Forge signature verification — local certificate/private-key ownership.** In the observed Expo CLI call, the signer must supply local certificate and private-key file paths, and the code checks the matching keypair; a self-signed certificate created by an attacker who already controls both files is not itself evidence of crossing VAYLET's release-signing boundary. However the verification routine is real, not dead code, and could matter if a future Expo release tool accepts lower-trust certificates or RSA signatures. Restrict release signing to owner-managed certificates/trust anchors, protect signing keys and do not enable arbitrary remote signing inputs. Follow `node-forge`/Expo upstream for a patched release, assess whether native build assets package this library, and re-review any signing workflow that adds external certificate input. Do not apply a fabricated patch version or disable verification to satisfy audit.

**Priority of remaining proof gaps (needs-review queue):** (1) `node-forge` — inventory and trust-boundary evidence for release-signing/native build pipelines; (2) `deepmerge-ts` — prove that no supported Prisma config-extension/plugin path receives lower-trust cyclic objects and qualify a v8 override if needed; (3) `mysql2` — confirm deployed build/CLI usage remains PostgreSQL-only and test a 3.23.1 targeted override if owners need a zero-High lockfile. These are *verification priorities*, not confirmed exploitation ranks. There are **zero confirmed attacker-to-vulnerable-sink paths** in the examined source.

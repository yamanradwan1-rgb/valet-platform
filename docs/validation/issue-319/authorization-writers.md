## Shared lock order and isolation constraints

1. **Canonical staff mutation:** for sensitive HTTP operations: current session/MFA assurance → transaction-scoped exclusive `hashtextextended('staff-management-org:' || organizationId,0)` → actor membership `FOR UPDATE` → active Location `FOR SHARE` (LM), target membership `FOR UPDATE`, grant mutation and audit. Code: `staff-management-authorization.ts:70-139`, `management-authorization.ts:95-166`; SQL reassertion `packages/database/prisma/migrations/20261001005000_mgt_240b_lm_staff_authority/migration.sql:4-72`. The SQL explicitly says not to acquire lifecycle advisory *after* org advisory (`20261001005000.../migration.sql:55-69`).
2. **Canonical existing-Location lifecycle:** optional settings-org lock → `location-lifecycle` exclusive → session/MFA → staff-org exclusive → membership and Location row locks → update. Code: `management-location.service.ts:268-295`; `common/database/location-lifecycle-lock.ts:3-18`. A reader taking lifecycle lock *after* staff-org risks a lock-order cycle, so do not suggest blindly adding it to #315 readers. The lifecycle writer takes the **staff-org** exclusive lock via Company Admin authorization. #315 tested Location-status SQL synthetically, but the #319 **real Location deactivation HTTP** tests now pass both reader-first (deactivation waits until the Dashboard HTTP read completes) and revoker-first (reader waits and is denied after commit), with PostgreSQL lock-wait traces (`docs/validation/issue-319/logs/audit-tests.txt:113-120`; `apps/api/test/dashboard-issue319-lifecycle.integration.test.ts`). That evidence covers these Dashboard/lifecycle interleavings, not every Physical Resources or discovery read.
3. **Account and token security:** login/refresh/global-disable take `staff-user-security` exclusive before updating User/session; logout has exact session `FOR UPDATE` instead (`staff-user-security-lock.ts:8-49`; `staff-auth.service.ts:95-146,187-203`; `staff-auth-logout.ts:15-26`; `tools/security-disable/persistence.ts:52-81`). MFA writers acquire session+User row locks before `mfa-user` (`mfa-session-repository.ts:17-42,64-92`). Onboarding activation takes account locks *before* staff-org (`20261001005300.../migration.sql:35-53`). These are different, not interchangeable fences.
4. **Isolation:** ordinary `inPostgresTransaction` issues plain `BEGIN`; PostgreSQL connection default is expected to be `READ COMMITTED` unless changed (`apps/api/src/common/database/postgres-transaction.ts:12-68`). #315 ordinary LM Dashboard read demands `READ COMMITTED` and takes **shared transaction** staff-org advisory *before repeating grant authorization* (`apps/api/src/modules/dashboard/dashboard-read-authorization.ts:37-88`). KPI instead obtains **shared session** staff-org advisory *before* starting its `REPEATABLE READ` snapshot, then releases it or discards the connection if ambiguous (`analytics-kpi-snapshot-transaction.ts:25-154`). Physical Resources overview starts `REPEATABLE READ` before authority evaluation but does not use either #315 fence (`physical-resource-read.service.ts:29-49`; `physical-resource-authorization.ts:19-54`). Do not attribute KPI protections to all RR endpoints.
5. **Reader exceptions:** `REPORT_EXPORT` does an exact current Staff session check *before* staff-org lock (`dashboard-read-authorization.ts:53-61`). Live history locks staff-user-security (shared), exact session (shared), CA MFA factor/session, staff-org (shared), entitlement row (shared) and membership/Location/grants through the projection (`live-history-read-authorization.ts:18-55,66-111,140-222`). Scope discovery uses exact session revalidation, but its Location/grant result is not fenced with staff-org (`dashboard-scope-discovery.service.ts:41-156`). Treat each route independently.

## Threat-model boundary

**Covered in the cooperative-lock guarantee:** HTTP/API canonical writers, current narrow SECURITY DEFINER functions, and specifically identified controlled operator commands with their documented locks. **Excluded:** ad hoc direct `DELETE membership_location_access`, `UPDATE organization_memberships/locations/users/organizations`, or entitlement edits issued as arbitrary DBA/owner SQL with no matching advisory lock. Row MVCC can expose pre-commit state to such readers despite a privileged writer's uncommitted change: an advisory lock cannot serialize an actor that does not take it (`dashboard-issue315-extended.integration.test.ts:199-214`). This exclusion is **not** an authorization to ignore runtime role grants or supported operator paths; it sets the limit of the stated #315/#319 proof.

Classifications above derive from source/previous test artifacts only. “Unverified” is not a confirmed exploit, and a green unit test alone is not deterministic two-connection HTTP validation. All #319 work should use the dedicated disposable PG test environment; this writer inventory performs no database operation.

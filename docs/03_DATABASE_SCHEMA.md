# Database Schema — Logical Design

## Issue #257 evidence-free result provenance — owner correction

Forward migration 067 initially adds nullable typed Operation `completion_basis`
with `OFF_NO_EVIDENCE`; forward 068 extends it with `NO_EFFECT_CONVERGENCE` as
documented in this file. Null retains the existing COMMITTED requirement
for a result Decision. Non-null is permitted only on COMMITTED with a real exact
result Shift, null Decision, bound request and bound policy. The insert/update
guard requires PENDING-to-COMMITTED, a live unconsumed exact Challenge and no
Decision for that operation. OFF_NO_EVIDENCE additionally requires current
effective action mode OFF; NO_EFFECT_CONVERGENCE records an already-satisfied
outcome without performing a new policy-gated effect. Terminal results,
scope/intent and one-time bindings remain immutable for owner and runtime alike.
Runtime receives only column-scoped completion-basis UPDATE; no broad UPDATE,
history rewrite, DELETE or trigger execution. There is no backfill or fake
evaluation. Existing FKs, indexes and 14d/90d/24m retention remain unchanged.
OFF's unused Challenge follows ordinary expiresAt+24h purge; Operation result
and no-evidence fingerprint recovery are independent of that ephemeral row.

## Phase 1 global conventions

These conventions are binding for Phase 1 unless superseded by an accepted decision.

### Identifiers

- Use PostgreSQL `uuid` columns consistently for entity identifiers.
- Phase 1 uses UUID v4-style cryptographically random, non-sequential identifiers generated by Prisma/application code.
- Do not introduce sequential public identifiers for guest/customer access.

### Time

- Store database timestamps as PostgreSQL `timestamptz(3)` in UTC.
- `created_at` defaults to server/database current time.
- `updated_at` is maintained by the application/ORM on mutation.
- Operational timestamps are server-authoritative; clients do not choose trusted operation time.
- Convert timestamps for display/reporting using the Location timezone.
- An Organization may span Locations in multiple timezones/countries; never assume one Organization timezone is authoritative for every Location.

### Controlled values

- Domain-controlled status/type values are represented as Prisma enums backed by PostgreSQL enum types unless a specific constraint requires another representation.
- Persist enum values using the explicit uppercase identifiers documented below.
- Do not add undocumented status values during implementation.

### Normalization

- Application/domain code performs normalization before persistence.
- Database constraints enforce uniqueness on normalized values where documented.
- Staff email is trimmed and lowercased before storage; `users.email` stores the normalized value.
- Staff/guest phone values, when normalized for international use, should use an E.164-compatible canonical representation; exact input UX is an application concern.
- `plate_country` is an uppercase ISO 3166-1 alpha-2 country code such as `JO`, `AE` or `SA`.
- Plate normalization is country-aware application behavior. Store raw and normalized plate values but do not invent one-country normalization rules.
- OCR/ANPR output is proposed input only; the confirmed/manual value is what the application persists as the operational plate value.

### Money

- Monetary values use PostgreSQL `numeric(14,3)` / Prisma Decimal, never floating-point types.
- Currency is an uppercase ISO 4217 three-letter code such as `JOD`, `AED` or `SAR`.
- Payment `service_amount` is the base valet charge before validation and tip.
- Validation `amount` is the reduction applied to the customer-responsible service amount; it is not a payment or a negative ledger entry.
- Payment `tip_amount` is the voluntary customer-paid amount in addition to the customer-responsible service amount.
- Payment `amount_due` is the final amount to collect directly from the customer after service responsibility and current validation, plus tip.
- Payment `amount_paid` is the current total actually collected from the customer.
- Refund `amount` is a positive amount returned or pending return from previously collected `amount_paid`.
- Net retained amount is derived as Payment `amount_paid - sum(SUCCEEDED Refund.amount)`; it is not duplicated on Payment.
- All monetary values in the accepted MVP financial contract are non-negative. CashEntry type represents decreases without storing negative money.
- Cross-row monetary invariants are enforced by locked transactional domain commands; do not claim a simple row CHECK can enforce aggregate totals.
- A Payment copies the Location currency when created. The immutable copy preserves historical meaning if Location configuration changes later.
- `numeric(14,3)` is the storage convention, not permission to accept unsupported fractional precision for every currency. Current Phase 6 monetary input boundaries validate exact representability against a reviewed checked-in registry derived from the SIX Financial Information ISO 4217 List One snapshot published `2026-01-01`; runtime network, `Intl`, CLDR/ICU, OS/browser locale data and provider defaults are not currency-precision authority.
- For an authoritative minor-unit exponent from 0 through 3, fractional digits beyond that exponent are accepted only when all are zero. No rounding or truncation is permitted. Missing/non-numeric exponents and exponents above storage scale 3 fail closed before mutation, with no guessed default.
- Provider adapters may convert validated decimal amounts to provider-specific minor units at integration boundaries.

### Tenant consistency

- Every business-owned operational record belongs to an Organization directly or through an enforced parent relation.
- Where a child stores `organization_id` plus another tenant-owned foreign key, the database must enforce that both point to the same Organization.
- Prefer composite foreign keys/unique constraints such as `(organization_id, resource_id)` where Prisma can model them cleanly.
- Use reviewed SQL migration constraints when Prisma cannot express a critical tenant invariant cleanly.
- `membership_location_access` includes `organization_id` so same-organization membership/location access can be database-enforced.
- Application authorization remains required even when the database also enforces tenant integrity.

### Referential delete behavior

- Do not cascade-delete operational history.
- Default foreign-key deletion behavior is `RESTRICT` / `NO ACTION` for operational and audit relationships.
- Configuration and people records are disabled/inactivated rather than deleted when referenced by history.
- Retention/anonymization behavior must follow later legal/business/configuration decisions; do not invent legal durations.

### Configuration First

Blueprint v1.0 requires normal operating-policy differences to be configurable, generally with:

```text
Company default -> Location override
```

This is a binding product requirement but does not authorize a speculative generic JSON settings table in the tenant/staff foundation.

Introduce typed configuration entities/columns in focused tasks when the corresponding policy is implemented.

DEC-042 adds typed Standard handoff policy:

```text

  NOT NULL DEFAULT EITHER

  PICKUP_CODE | DYNAMIC_QR | EITHER | NULL
```

Effective policy is Location override when non-null, otherwise Company default.

```text
  valet_service_fee = 0
  payment_service_payer = CUSTOMER

  tips_enabled = false
```

Location currency remains separate and authoritative.

### Phase 1 migration policy

- The first implemented schema task creates the initial migration.
- Each later database task adds a new migration when the schema changes.
- Never rewrite an already-applied migration to hide a later change.

### Production database connection boundary

Accepted DEC-025 keeps the schema at exactly 18 forward-only migrations while
hardening how production identities reach PostgreSQL:

- the API runtime receives only query-free `DATABASE_URL` and configures strict
  certificate-verifying TLS through Node `pg` options;
- the API fails startup if the migration/admin credential is present;
- before serving production traffic, the live runtime connection must prove TLS
  through its own `pg_stat_ssl` row and prove the connected role has no elevated
  flags, database/schema ownership, `CREATE` capability, or ownership of public
  application tables, sequences, or functions;
- migration/admin commands receive `MIGRATION_DATABASE_URL` only in their
  controlled job boundary, with exact `sslmode=require`, `sslaccept=strict`, and
  optional `sslrootcert` production parameters;
- production migration/provisioning verifies its own live `pg_stat_ssl` row
  before schema or privilege mutation; and
- runtime and migration roles and production passwords remain distinct.

These connection checks do not change table persistence or replace the explicit
runtime `GRANT`/`REVOKE` contract.

(`location_configuration_set_override`,
`location_configuration_clear_override`) plus private authorization/state/audit

public` and PUBLIC execution revoked; the runtime role receives EXECUTE only on

`locations` (no generic UPDATE). Each call revalidates an ACTIVE
`LOCATION_MANAGER` membership with explicit same-Organization Location access
inside the database, rejects unknown settings/values (`22023`), compares the
caller's `expected_updated_at` against the locked `locations.updated_at`

persisted Location currency using the private checked-in
`location_configuration_minor_unit_exponent` mapping (unknown or unusable
precision fails closed; no silent rounding). Failed calls write no
configuration change and no audit. Organization default columns are not writable
through this surface.

### MGT-BE-05 Management settings and branding authority (migration 38)

Migration `20260916003800_mgt_be_05_company_settings_branding` keeps the ten
existing typed default/override pairs and adds only typed DEC-083 state. There
is no `organization_settings`/`location_settings` JSONB, generic rules table, or
arbitrary string-key mutation API.

Operating hours are normalized in `organization_operating_hours` and
`location_operating_hours_overrides`. Each configured schedule is exactly seven
weekday rows with either CLOSED (`opens_at`/`closes_at` null) or one same-day
OPEN interval where `opens_at < closes_at`. Both time columns are PostgreSQL
`time without time zone`; no UTC offset is persisted. Absence of Company rows is
an unconfigured Company schedule. Absence of Location rows means inherit the
current Company schedule; CLEAR deletes the override rows rather than copying a
default into them.

Company Admin settings/branding writes execute only through migration-owned,
fixed-`search_path` `SECURITY DEFINER` functions. Public EXECUTE is revoked and
the runtime role receives only the reviewed mutation entry points. Runtime
retains no generic `UPDATE organizations`, no generic `UPDATE locations`, and no
direct arbitrary INSERT/UPDATE/DELETE authority on the operating-hours tables.
The functions revalidate current Organization/Admin/Location authority,
implement optimistic concurrency against the authoritative Organization or
Location `updated_at`, advance revisions monotonically for real changes, treat
desired-state no-ops as audit-free/no-CAS convergence, and append one truthful
same-transaction `AuditEvent`. SET rejects SQL NULL; Location CLEAR is explicit.

Company settings and Location setting mutations serialize on the same
per-Organization Management settings transaction boundary. Operational commands
that make mutable policy decisions acquire the corresponding shared boundary
before later policy-dependent row locks, so a committed writer or the command's
earlier snapshot wins coherently without holding the boundary across external
provider I/O.

### MGT-BE-07 Location lifecycle authority (migration 40)

Migration `20260917004000_mgt_be_07_location_management` adds only the smallest
DEC-094 lifecycle representation: `locations.accepting_intake BOOLEAN NOT NULL
DEFAULT FALSE`, backfills existing rows to `true` exactly when their existing
status is `ACTIVE`, changes the Location status default to `INACTIVE`, and adds
the CHECK that prevents inactive Locations from accepting intake. Existing
historical rows and their status are not rewritten beyond the intake backfill.

Management creation writes `INACTIVE/false` explicitly and uses the caller's
stable `operationId` as Location-create retry identity. A partial unique
`audit_events(organization_id, idempotency_key)` index for `LOCATION_CREATED`
prevents duplicate create success under concurrent retries; identical immutable
request facts converge and conflicting operation-id reuse fails closed.

Activation changes `INACTIVE/false -> ACTIVE/true` only when the persisted
currency is supported and the persisted timezone is a valid IANA timezone.
Those are the complete BE-07 readiness checks. Stop-intake changes
`ACTIVE/true -> ACTIVE/false`. Deactivation changes
`ACTIVE/false -> INACTIVE/false` only when no non-`COMPLETED` ValetSession, no
`ACTIVE` Shift, and no Task in `QUEUED`, `ASSIGNED`, `ACCEPTED`, or
`IN_PROGRESS` exists for the exact Organization/Location.

Lifecycle and correction mutations use the shared `location-lifecycle:<uuid>`
transaction advisory boundary. Management lifecycle mutations take the exclusive
form; operational paths that must remain coherent with deactivation use the
shared form. Check-In additionally requires `ACTIVE` plus
`accepting_intake = true`, while existing-session drain work may continue while
the Location remains `ACTIVE` with intake closed. Final deactivation rechecks the
three bounded blocker classes under the lifecycle boundary.

Currency and timezone correction require the Location to be `INACTIVE`, intake
closed, and drained by those same three blocker checks. Currency correction also
requires a supported currency and exact representability of the current effective
valet service fee in that currency. Timezone correction requires a bounded
non-control reason and valid IANA timezone; it changes only the current Location
timezone and does not rewrite historical timestamps or report facts.

Real mutations append one Location-scoped event atomically from the bounded
family `LOCATION_CREATED`, `LOCATION_ACTIVATED`, `LOCATION_INTAKE_STOPPED`,
`LOCATION_DEACTIVATED`, `LOCATION_CURRENCY_CORRECTED`, and
`LOCATION_TIMEZONE_CORRECTED`. Runtime mutation remains behind the reviewed
migration-owned `SECURITY DEFINER` entry points; helper/PUBLIC execution stays
denied. A migration-owned audit trigger also reserves those six event names from
direct runtime `audit_events` INSERT, so the create idempotency ledger and
lifecycle audit provenance cannot be forged outside the lifecycle commands.
Representative 100,001-row blocker plans proved the existing
ValetSession/Task indexes insufficient for the negative-state predicates, so
migration 40 adds partial indexes
`valet_sessions_location_id_non_completed_idx` and
`tasks_location_id_non_terminal_idx`. The existing
`shifts_location_id_status_idx` remains sufficient; no additional Shift blocker
index is added.

Constraints/rules:

- restrictive User foreign key

## user_mfa_totp_factors

```text
id
user_id
state
protected_secret
last_accepted_step nullable
recovery_set_generation
created_at
activated_at nullable
retired_at nullable
```

State:

- `PENDING`
- `ACTIVE`
- `RETIRED`

Rules:

- restrictive User foreign key and at most one live (`PENDING` or `ACTIVE`)
  factor per User
- TOTP is SHA-1, six digits, 30-second period, accepted only within ±1 period;
  each generated secret is 20 random bytes encoded as 32 uppercase Base32
  characters; provisioning identifies the issuer as `VAYLET`
- `protected_secret` is an `mte1` AES-256-GCM envelope. Encryption uses
  `MFA_TOTP_ENCRYPTION_KEY_B64URL`, exactly 32 random bytes encoded as canonical
  unpadded base64url (43 characters). The envelope is
  `mte1.<12-byte IV>.<ciphertext>.<16-byte tag>` using canonical unpadded
  base64url components, with User/factor identity bound as AAD
- accepted TOTP time steps advance monotonically so an accepted step cannot be
  replayed
- factor identity/protected material and recorded activation/retirement times
  are immutable; `RETIRED` never reactivates
- recovery-set generation starts at zero and advances exactly by one when a new
  ten-code set is issued

## mfa_recovery_codes

```text

verifier
created_at
consumed_at nullable
```

Rules:

- restrictive factor foreign key; slots are exactly 1 through 10 and unique per
  factor/generation, so each issued generation contains exactly ten codes
- raw code wire format is `vmr1-<selector>-<secret>`, where selector is 8 random
  bytes and secret is 20 random bytes, both canonical unpadded base64url
- only the selector plus an `mrv1` HMAC-SHA-256 verifier are persisted. HMAC uses
  `MFA_RECOVERY_HMAC_SECRET_B64URL`, exactly 32 random bytes encoded as canonical
  unpadded base64url (43 characters), and binds User, factor, generation,
  selector, and raw code
- verifier comparison is constant-time; a consumed code cannot be reused or
  un-consumed

## anti_abuse_events

```text

scope
key_hash
occurred_at
state
```

State:

- `PENDING`
- `COUNTED`
- `IGNORED`

Rules:

- ephemeral shared PostgreSQL enforcement state under accepted DEC-024; it is not tenant business history and is never copied to AuditEvent
- scopes are exactly `v1:staff-login-identifier`, `v1:staff-client-address`,

  the User in the immediately preceding 15 minutes; successful verification
  finalizes its reservation to ignored rather than erasing earlier failures

  at most 20 changed creates per Organization and 5 changed resends per target
  membership; durable same-operation reconciliation consumes no new slot

- index `(scope, key_hash, occurred_at)` supports exact current-window lookup; a separate occurrence-time index supports fixed retention cleanup
- ordinary runtime access is limited to select, insert of scope/hash/state and update of state; it has no direct delete, truncate, DDL or ownership authority

- `amount_due = effective customer service due + tip_amount`
- `VENUE` expresses responsibility for the base service charge only; it does not create Venue Client identity, venue receivable or settlement persistence
- `service_payer` may be corrected only through the guarded pre-collection rule below; outside that rule it is immutable
- guarded payer correction requires all of: `amount_paid = 0`, no CashEntry, no Validation history, and no provider transaction/reference has started; the authorized correction recomputes projections and writes required AuditEvent atomically
- `tip_amount` remains on Payment because MVP has no tip distribution/payroll lifecycle; it is included in `amount_due` for both cash and digital collection
- non-null provider references are unique by `(organization_id, provider, provider_reference)`
- Refund state is not copied onto Payment; a paid Payment remains `PAID` while Refund rows preserve refund lifecycle/history
- no separate Tip table is created
- Payment status remains independent from ValetSession state
- pre-collection `service_amount`, `tip_amount`, current Validation and the narrowly guarded `service_payer` may be corrected only through explicit authorized transactions that preserve required history, recompute `amount_due` and write required audit
- a pre-collection recomputation that makes `amount_due = 0` must atomically set `collection_method = NONE`, `status = NOT_REQUIRED`, `amount_paid = 0`, and clear provider/reference
- a pre-collection recomputation that changes zero due to `amount_due > 0` must atomically select `CASH` or `DIGITAL`, set `status = UNPAID`, keep `amount_paid = 0`, and satisfy the selected method's provider-field rules
- after any collection or provider transaction has started, monetary responsibility/terms are not silently rewritten and returned value uses Refund where applicable
- split tender, multiple successful collections and installment payment are not accepted MVP persistence behavior; one Payment has one collection method
- no normal hard delete
- initial creation snapshots current effective typed policy and authoritative Location currency; later policy changes do not rewrite the canonical Payment
- initial `tip_amount = 0`; CUSTOMER owes the service amount, while VENUE keeps the service amount snapshot but owes zero customer service amount
- zero due initializes as exact `NONE / NOT_REQUIRED`; positive `CASH_ONLY` and `CASH_OR_DIGITAL` initialize as `CASH / UNPAID`
- positive `DIGITAL_ONLY` fails closed before any Payment or AuditEvent because no real provider is activated; zero-due `DIGITAL_ONLY` remains valid as `NONE / NOT_REQUIRED`
- initialization locks the authoritative ValetSession and commits the first Payment plus one `PAYMENT_INITIALIZED` AuditEvent atomically; retries return the existing historical projection without rewriting it

Required row-local Payment matrix:

- `collection_method = NONE` requires status `NOT_REQUIRED`, `amount_due = 0`, `amount_paid = 0`, null provider and null provider reference
- status `NOT_REQUIRED` requires `collection_method = NONE`
- `collection_method = CASH` requires null provider and null provider reference
- `collection_method = DIGITAL` requires non-null provider; provider reference may be null only while status is `UNPAID` before a reference exists, or while status is `FAILED` when the failed attempt did not create a reference
- status `UNPAID` requires a positive unpaid balance (`amount_due > amount_paid`), no authoritative digital result pending, and collection method `CASH` or `DIGITAL`; a digital UNPAID row requires non-null provider
- status `PENDING` requires collection method `DIGITAL`, non-null provider, non-null provider reference and `amount_paid = 0`
- status `FAILED` requires collection method `DIGITAL`, non-null provider and a positive unpaid balance (`amount_due > amount_paid`)
- status `PAID` requires collection method `CASH` or `DIGITAL`, `amount_due > 0`, `amount_paid = amount_due` and non-null `paid_at`

Every field-to-field implication in this row-local matrix, together with the non-negative money and `amount_paid <= amount_due` rules, is intended to be enforced with database CHECK constraints. Provider/reference uniqueness is a database unique constraint. The current-Validation formula, guarded payer correction, allowed pre-collection correction transaction, cash aggregate and refund aggregate cross rows and must instead be enforced by locked transactional domain logic plus tests. Do not add a database trigger that makes payer absolutely immutable and thereby blocks the accepted guarded correction.

  event-type query shapes from full-table scan plus top-N sort to ordered index

Organization-wide audit uses stable event UUIDs for retryable internal writes.
An exact retry with identical immutable facts converges to the existing row;
reusing the same UUID with different immutable facts fails the caller
transaction. The existing nullable/non-unique `idempotency_key` remains

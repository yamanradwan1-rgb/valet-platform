# Database Schema — Logical Design

Status: Binding  
Version: 0.6

Database: PostgreSQL  
ORM: Prisma

## Phase 1 global conventions

These conventions are binding for Phase 1 unless superseded by an accepted decision.

### Identifiers

- Use PostgreSQL `uuid` columns consistently for entity identifiers.
- Phase 1 uses UUID v4-style cryptographically random, non-sequential identifiers generated by Prisma/application code.
- Do not introduce sequential public identifiers for guest/customer access.

### Time

- Store database timestamps as PostgreSQL `timestamptz(3)` in UTC.
- `created_at` defaults to server/database current time.
- `updated_at` is maintained by the application/ORM on mutation.
- Operational timestamps are server-authoritative; clients do not choose trusted operation time.
- Convert timestamps for display/reporting using the Location timezone.
- An Organization may span Locations in multiple timezones/countries; never assume one Organization timezone is authoritative for every Location.

### Controlled values

- Domain-controlled status/type values are represented as Prisma enums backed by PostgreSQL enum types unless a specific constraint requires another representation.
- Persist enum values using the explicit uppercase identifiers documented below.
- Do not add undocumented status values during implementation.

### Normalization

- Application/domain code performs normalization before persistence.
- Database constraints enforce uniqueness on normalized values where documented.
- Staff email is trimmed and lowercased before storage; `users.email` stores the normalized value.
- Staff/guest phone values, when normalized for international use, should use an E.164-compatible canonical representation; exact input UX is an application concern.
- `plate_country` is an uppercase ISO 3166-1 alpha-2 country code such as `JO`, `AE` or `SA`.
- Plate normalization is country-aware application behavior. Store raw and normalized plate values but do not invent one-country normalization rules.
- OCR/ANPR output is proposed input only; the confirmed/manual value is what the application persists as the operational plate value.

### Money

- Monetary values use PostgreSQL `numeric(14,3)` / Prisma Decimal, never floating-point types.
- Currency is an uppercase ISO 4217 three-letter code such as `JOD`, `AED` or `SAR`.
- Payment `service_amount` is the base valet charge before validation and tip.
- Validation `amount` is the reduction applied to the customer-responsible service amount; it is not a payment or a negative ledger entry.
- Payment `tip_amount` is the voluntary customer-paid amount in addition to the customer-responsible service amount.
- Payment `amount_due` is the final amount to collect directly from the customer after service responsibility and current validation, plus tip.
- Payment `amount_paid` is the current total actually collected from the customer.
- Refund `amount` is a positive amount returned or pending return from previously collected `amount_paid`.
- Net retained amount is derived as Payment `amount_paid - sum(SUCCEEDED Refund.amount)`; it is not duplicated on Payment.
- All monetary values in the accepted MVP financial contract are non-negative. CashEntry type represents decreases without storing negative money.
- Cross-row monetary invariants are enforced by locked transactional domain commands; do not claim a simple row CHECK can enforce aggregate totals.
- A Payment copies the Location currency when created. The immutable copy preserves historical meaning if Location configuration changes later.
- `numeric(14,3)` is the storage convention, not permission to accept unsupported fractional precision for every currency. Before persistence and before provider conversion, domain/provider commands must validate or deterministically quantize amounts to the Payment currency's supported minor-unit exponent.
- Silent rounding that materially changes a user-entered or provider-authoritative amount is not allowed. The financial command/provider integration must use one documented deterministic precision rule and reject values that cannot be safely represented under that rule.
- Provider adapters may convert validated decimal amounts to provider-specific minor units at integration boundaries.

### Tenant consistency

- Every business-owned operational record belongs to an Organization directly or through an enforced parent relation.
- Where a child stores `organization_id` plus another tenant-owned foreign key, the database must enforce that both point to the same Organization.
- Prefer composite foreign keys/unique constraints such as `(organization_id, resource_id)` where Prisma can model them cleanly.
- Use reviewed SQL migration constraints when Prisma cannot express a critical tenant invariant cleanly.
- `membership_location_access` includes `organization_id` so same-organization membership/location access can be database-enforced.
- Application authorization remains required even when the database also enforces tenant integrity.

### Referential delete behavior

- Do not cascade-delete operational history.
- Default foreign-key deletion behavior is `RESTRICT` / `NO ACTION` for operational and audit relationships.
- Configuration and people records are disabled/inactivated rather than deleted when referenced by history.
- Retention/anonymization behavior must follow later legal/business/configuration decisions; do not invent legal durations.

### Configuration First

Blueprint v1.0 requires normal operating-policy differences to be configurable, generally with:

```text
Company default -> Location override
```

This is a binding product requirement but does not authorize a speculative generic JSON settings table in the tenant/staff foundation.

Introduce typed configuration entities/columns in focused tasks when the corresponding policy is implemented.

### Phase 1 migration policy

- The first implemented schema task creates the initial migration.
- Each later database task adds a new migration when the schema changes.
- Never rewrite an already-applied migration to hide a later change.

## payments

```text
id
organization_id
location_id
valet_session_id
service_payer
collection_method
currency
service_amount
tip_amount
amount_due
amount_paid
status
creation_idempotency_key
provider nullable
provider_reference nullable
created_at
updated_at
paid_at nullable
```

Service payer:

- CUSTOMER
- VENUE

Collection method:

- NONE
- CASH
- DIGITAL

Payment status:

- NOT_REQUIRED
- UNPAID
- PENDING
- PAID
- FAILED

Rules:

- at most one Payment per ValetSession, enforced by unique `(organization_id, valet_session_id)`
- create the Payment when the session's financial policy is evaluated; absence means not yet evaluated and must never be interpreted as `NOT_REQUIRED`
- Location and ValetSession must belong to `organization_id`, and the ValetSession must belong to the stored Location
- `currency` is copied from the authoritative Location at creation and is immutable
- `creation_idempotency_key` is required and unique within Organization
- monetary columns use `numeric(14,3)`
- `service_amount >= 0`
- `tip_amount >= 0`
- `amount_due >= 0`
- `amount_paid >= 0` and `amount_paid <= amount_due`
- effective customer service due is `service_amount - current_validation.amount` for `CUSTOMER` (validation amount is treated as `0` when there is no current row), or `0` for `VENUE`
- `amount_due = effective customer service due + tip_amount`
- `VENUE` expresses responsibility for the base service charge only; it does not create Venue Client identity, venue receivable or settlement persistence
- `service_payer` may be corrected only through the guarded pre-collection rule below; outside that rule it is immutable
- guarded payer correction requires all of: `amount_paid = 0`, no CashEntry, no Validation history, and no provider transaction/reference has started; the authorized correction recomputes projections and writes required AuditEvent atomically
- `tip_amount` remains on Payment because MVP has no tip distribution/payroll lifecycle; it is included in `amount_due` for both cash and digital collection
- non-null provider references are unique by `(organization_id, provider, provider_reference)`
- Refund state is not copied onto Payment; a paid Payment remains `PAID` while Refund rows preserve refund lifecycle/history
- no separate Tip table is created
- Payment status remains independent from ValetSession state
- pre-collection `service_amount`, `tip_amount`, current Validation and the narrowly guarded `service_payer` may be corrected only through explicit authorized transactions that preserve required history, recompute `amount_due` and write required audit
- a pre-collection recomputation that makes `amount_due = 0` must atomically set `collection_method = NONE`, `status = NOT_REQUIRED`, `amount_paid = 0`, and clear provider/reference
- a pre-collection recomputation that changes zero due to `amount_due > 0` must atomically select `CASH` or `DIGITAL`, set `status = UNPAID`, keep `amount_paid = 0`, and satisfy the selected method's provider-field rules
- after any collection or provider transaction has started, monetary responsibility/terms are not silently rewritten and returned value uses Refund where applicable
- split tender, multiple successful collections and installment payment are not accepted MVP persistence behavior; one Payment has one collection method
- no normal hard delete

Required row-local Payment matrix:

- `collection_method = NONE` requires status `NOT_REQUIRED`, `amount_due = 0`, `amount_paid = 0`, null provider and null provider reference
- status `NOT_REQUIRED` requires `collection_method = NONE`
- `collection_method = CASH` requires null provider and null provider reference
- `collection_method = DIGITAL` requires non-null provider; provider reference may be null only while status is `UNPAID` before a reference exists, or while status is `FAILED` when the failed attempt did not create a reference
- status `UNPAID` requires a positive unpaid balance (`amount_due > amount_paid`), no authoritative digital result pending, and collection method `CASH` or `DIGITAL`; a digital UNPAID row requires non-null provider
- status `PENDING` requires collection method `DIGITAL`, non-null provider, non-null provider reference and `amount_paid = 0`
- status `FAILED` requires collection method `DIGITAL`, non-null provider and a positive unpaid balance (`amount_due > amount_paid`)
- status `PAID` requires collection method `CASH` or `DIGITAL`, `amount_due > 0`, `amount_paid = amount_due` and non-null `paid_at`

Every field-to-field implication in this row-local matrix, together with the non-negative money and `amount_paid <= amount_due` rules, is intended to be enforced with database CHECK constraints. Provider/reference uniqueness is a database unique constraint. The current-Validation formula, guarded payer correction, allowed pre-collection correction transaction, cash aggregate and refund aggregate cross rows and must instead be enforced by locked transactional domain logic plus tests. Do not add a database trigger that makes payer absolutely immutable and thereby blocks the accepted guarded correction.

## validations

```text
id
organization_id
payment_id
mode
amount
is_current
supersedes_validation_id nullable
applied_by_membership_id
applied_at
created_at
```

Mode:

- NONE
- FULL
- PARTIAL

Rules:

- Validation belongs to Payment; Organization, ValetSession and Location are inherited through the tenant-safe Payment relation rather than duplicated
- applying membership belongs to the same Organization and must be authorized for the Payment's Location in application code
- no initial validation is represented by no current row
- Validation is permitted only for a Payment whose `service_payer = CUSTOMER`; guarded payer correction is allowed only before any Validation history exists, so current/historical Validation can never become attached to a later `VENUE` Payment
- `NONE` is used only as an explicit superseding correction and requires `amount = 0`
- `FULL` requires `amount > 0`; transactional domain logic requires it to equal Payment `service_amount`
- `PARTIAL` requires `amount > 0`; transactional domain logic requires it to be less than Payment `service_amount`
- multiple history rows may exist, but a partial unique index permits at most one current Validation per Payment where `is_current = true`
- a correction atomically marks the previous row non-current, inserts a new row pointing to the previous row, recalculates Payment `amount_due`, applies the required zero/positive due transition when necessary, and writes the required AuditEvent
- mode, amount, actor and timestamps on historical rows are immutable; rows are not deleted
- same-Payment supersession and tenant ownership must be database-enforced where practical

## payment_provider_events

```text
id
organization_id
payment_id
refund_id nullable
provider
provider_event_id
provider_reference nullable
processing_status
received_at
processed_at
safe_result_code nullable
created_at
```

Processing status:

- PROCESSED
- IGNORED

Rules:

- used only for provider-neutral digital Payment/Refund callback idempotency
- Payment and optional Refund must belong to the same Organization, and optional Refund must belong to the referenced Payment
- unique `(organization_id, provider, provider_event_id)` prevents duplicate callback mutation
- `provider_reference` preserves the safe transaction/order reference carried by that event when present
- after provider signature verification and adapter normalization, ProviderEvent insert, Payment/Refund mutation and required AuditEvent must commit in one database transaction
- `received_at` and `processed_at` are server-authoritative; every durable row has a committed processing outcome
- the first valid callback is normalized and transactionally committed as `PROCESSED` when its recognized financial result is applied, or `IGNORED` when it is valid but intentionally causes no financial mutation
- duplicate delivery after commit finds the existing unique provider event row and does not repeat Payment/Refund mutation or AuditEvent
- if processing fails before commit, the entire transaction rolls back; no durable ProviderEvent row remains and provider retry may safely execute again
- PaymentProviderEvent is not a durable asynchronous inbox; `PROCESSED` and `IGNORED` are the only durable statuses and both describe committed outcomes
- internal processing failure is not persisted as a ProviderEvent status; provider-reported financial failure is represented by Payment/Refund lifecycle while its successfully handled ProviderEvent is `PROCESSED`
- a valid successful collection callback atomically sets Payment `amount_paid = amount_due`, status `PAID` and server-authoritative `paid_at`; partial digital capture is not part of the accepted MVP contract
- store only identifiers, safe classification/result and timestamps needed for processing/audit
- never store raw callback payload, PAN, CVV, reusable token, provider credential or secret
- provider-specific event names/payload mapping remain in the adapter, not the core schema
- Payment `creation_idempotency_key` protects Payment creation and ProviderEvent uniqueness protects committed callback replay; neither alone proves safe outbound provider-operation retries after Payment creation
- Phase 6's selected-provider integration must define stable outbound initiation/refund idempotency and explicit handling of callbacks whose provider reference is stale/superseded by a later retry
- no separate PaymentAttempt entity is required for Phase 1; add one later only if the selected provider demonstrates a concrete safety requirement that cannot be met with the accepted aggregate/event model

## refunds

```text
id
organization_id
payment_id
amount
reason
status
authorized_by_membership_id
idempotency_key
provider nullable
provider_reference nullable
requested_at
completed_at nullable
created_at
```

Status:

- PENDING
- SUCCEEDED
- FAILED

Rules:

- Refund is a separate append-only entity; Payment has no `REFUNDED` status
- amount uses `numeric(14,3)` and must be greater than zero
- reason is required, trimmed and non-empty
- authorizing membership and Payment must belong to the same Organization; Location permission and role authorization remain application checks
- `VALET_EMPLOYEE` is never authorized to issue a refund
- `idempotency_key` is required and unique within Organization
- cash refund is created as `SUCCEEDED` atomically with cash handling and `completed_at`
- cash refund requires null provider/provider reference
- digital refund begins `PENDING` and requires non-null provider
- digital `PENDING` and `FAILED` require provider and require `completed_at IS NULL`
- every `SUCCEEDED` refund requires non-null `completed_at`
- successful digital refund requires non-null provider and non-null provider reference
- any non-null `provider_reference` requires non-null provider
- non-null refund provider references are unique by `(organization_id, provider, provider_reference)`
- these provider/status/completion implications are row-local and are intended for database CHECK constraints in the Refund persistence slice
- multiple refunds are allowed; full versus partial is derived from remaining refundable balance and is not another persisted type
- successful refunded total is the sum of `SUCCEEDED` Refund amounts; pending amounts reserve refundable balance but are not yet returned
- in one locked transaction, application logic must enforce `new refund amount <= amount_paid - sum(existing PENDING and SUCCEEDED refund amounts)`
- cross-row refund totals cannot be enforced with a simple CHECK constraint and must be covered by concurrency/integration tests
- refund authorization, Refund mutation and required AuditEvent commit atomically
- failed/superseded Refund rows remain historical and are not hard-deleted

Financial tenant/location ownership:

- Payment stores `organization_id`, `location_id` and `valet_session_id` and uses composite tenant/location-safe foreign keys
- Validation, CashEntry, PaymentProviderEvent and Refund store `organization_id` plus `payment_id`; they derive ValetSession/Location from Payment instead of duplicating those identifiers
- every child uses a composite same-Organization Payment relation
- applying/collecting/adjusting/refunding membership fields use same-Organization composite relations; application authorization additionally verifies Location access and role
- all financial parent, actor and history relationships use `RESTRICT` / `NO ACTION`; normal application behavior never cascade-deletes financial history

## Deletion policy

Do not cascade-delete operational history.

Prefer disable/archive/inactivate for configuration and people records.

Retention duration remains a legal/business/configuration decision and may vary by customer/country.

## Atomic transaction rules

Must be atomic where applicable:

- protected state transition + audit event
- parking assignment + audit
- key assignment/movement + custody/audit event
- task assignment/reassignment/acceptance + dispatch/audit event
- handoff verification + completion + audit
- supervisor override + reason + audit
- protected financial mutation + financial/audit event

## Idempotency

Design retry safety for:

- customer retrieval request
- payment webhook

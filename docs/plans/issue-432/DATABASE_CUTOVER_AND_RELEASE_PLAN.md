## Two **independent** source-writer cutovers

**Phase 1 — Dispatch QUEUED / DECLINED legacy clock.** `apps/api/src/modules/dashboard/management-alert-clock-cutover.ts:1–31` requires `MANAGEMENT_ALERTS_PHASE1_DISPATCH_POST_LOCK_CUTOVER` in exact UTC ISO millisecond `YYYY-MM-DDTHH:mm:ss.SSSZ`; absent/invalid config fails closed. Older source transactions used transaction-start time that could precede locks and yield misleading queue duration. The corrected writer shares one **post-lock database** instant between canonical Task/Dispatch/Audit and relevant guest retrieval records. Current Episode identity is proven by Task version and matching event; duplicate/ambiguous evidence fails closed (`docs/plans/ISSUE_414_PHASE1_DISPATCH_CHRONOLOGY_EVIDENCE.md:10–123`).

**Phase 2/3 — stage ACCEPTED / IN_PROGRESS / READY / HANDOFF_PENDING.** `apps/api/src/modules/dashboard/management-alert-sources/retrieval-phase-stage-clock-cutover.ts:1–33` separately requires `MANAGEMENT_ALERTS_PHASE23_STAGE_POST_LOCK_CUTOVER`. This proves post-fix **stage writer** provenance only. The Phase 1 Dispatch timestamp is **never** a fallback, even if both environment strings parse. ALT-04/06 require stage/READY clock and current episode proof; source ambiguity means no case (DEC-110 lines 36–42).

For **each** cutover, the release owner must first deploy and attest the fixed writer build SHA with alert flags OFF, then demonstrate that every old binary, worker, replica and in-flight write using that writer is quiescent. Capture the database server clock **after** complete quiescence with an explicit UTC representation accepted by the exact-UTC parser:

```sql
SELECT to_char(
  clock_timestamp()::timestamptz(3) AT TIME ZONE 'UTC',
  'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'
) AS post_lock_clock_cutover;
```

Preserve the exact returned UTC millisecond string and evidence of fixed-writer deployment SHA, all replica/worker versions, old-version inventory, transaction drain, target DB identity, capture time, responsible operator and subsequent new-writer event strictly after the cutoff. The `AT TIME ZONE 'UTC'` conversion is deliberate: raw `timestamptz` display follows the SQL session timezone and may not render the parser's required `Z` form. Never infer the cutoff from build time, app host clock, raw microsecond timestamp rounded in JavaScript, another environment, or a test fixture. Source events at or before the cutoff are ineligible (`episode_time > cutover` is strict). The fractional-millisecond counterexample and corrected test are documented at `docs/plans/ISSUE_414_PHASE1_DISPATCH_CHRONOLOGY_EVIDENCE.md:172–205`. If quiescence or DB-side precision cannot be proven, retain affected categories OFF, regardless of green synthetic tests. Relevant post-lock source calls are `queue-parking-task-command.ts:68–80`, `decline-task-command.ts:22–35`, `guest-retrieval-request-command.ts:147–155`, `accept-task-command.ts:21–34`, `start-retrieval-command.ts:51–84`, `mark-ready-command.ts:45–79`, and `initiate-handoff-command.ts:23–40`.

## Monitoring and stop conditions

Measure preview and exact detail error codes, nondisclosing denied vs no-source behavior, age of visible occurrences, conditional overlap/retirement, unseen count mismatch, Seen conflict/idempotent retries, 401/authorization/MFA assurance rejection, source unavailability, and DB lock/pool waits. Record per-family SQL/HTTP median, p95, max and `EXPLAIN (ANALYZE, BUFFERS)` over sparse and dense organizations, 25/100/200 foreground-tab bursts and real response-cache behavior. Keep tenant and payload IDs sanitized in telemetry; do not log source selectors, sensitive reasons, GPS, payment, audit internals or guest tokens. Missing/invalid cutover, cross-tenant/Location leakage, Seen/source-authority mismatch, seven-day boundary disagreement, inaccurate active state, unsafe source privilege, false-zero on source failure, unbounded query or unacceptable pool saturation is a stop/disable condition. No alert GET may hold up operational Task/payment writers indefinitely.

## Safe rollback and recovery

Disable server P23 first and P1 if necessary; disable corresponding browser flags, stop background/foreground polling and invalidate visible stale/cached alert responses. `NEXT_PUBLIC_*` switches are embedded in the Next.js browser bundle: a running client does **not** immediately lose a compiled-in bell because a server environment variable changes. Serve a rebuilt OFF-bundle or revert to the known compatible OFF frontend while the API gate denies requests. Verify server endpoints actually deny new feature access before considering client rollout complete. Leave deployed canonical Task/Session/Shift/payment writers alone if separately approved and healthy; **never revert to a pre-fix writer while retaining the old cutover as trustworthy**. If old code is restored, consider its chronology untrusted and require a new writer-drain/DB-cutover sequence before re-enabling affected alerts. Keep additive tables, source events, preference revisions, Seen timestamps, audit history and all FKs intact. No down migration, counter reset, event deletion, automatic Seen purge or fabricated backfill. Keep standard business functionality usable, with alerts OFF.

# Issue #432 — Management Alerts prototype security and authorization model

**Status:** Design contract for an isolated prototype; no authorization to deploy, change production access, run migrations, or turn on alerts. Reviewed repository snapshot: `a9c1c06c6632ac9d8f61a7fc8f8f0e87ba207bca` (2026-11-12). The prototype may illustrate these rules using explicitly synthetic data; its UI is not evidence that live authorization works.

## Binding policy and limits

- DEC-109 (Accepted, lines 9–60) fixes Phase 1 timing, recipient and personal preference policy; DEC-110 (Accepted, lines 12–46) defines Phase 2 source rights, committed occurrence identity and Seen; DEC-111 (Accepted, lines 12–55) defines Phase 3 financial, staff, Shift and commercial boundaries.
- DEC-107 **still says Proposed** at line 3, despite approved Issue #352 directions and committed emergency-takeover source. Do not silently upgrade its status. ALT-05 must follow the approved, source-proven takeover operation and any unresolved compatibility review before activation (DEC-110 lines 8–25).
- Existing product authority for Staff session, tenant membership, exact selected active Location, effective entitlement, MFA and source-specific privilege remains authoritative. A bell, dashboard route, payload, local UI state, or remembered source ID conveys no access.
- The alert layer reads persisted operational facts. A preview, detail, poll, badge or Seen must never perform Task/Session, custody, Shift, payment, collection, audit-history or provider command mutation. An alert is not an operational approval.

## Authorization sequence and response discipline

1. Resolve the Staff bearer from the `Authorization` header. `DatabaseStaffSessionContextResolver` hashes the presented credential and checks the current hash, revocation, access/absolute expiry and active User (`apps/api/src/modules/auth/staff-session-context.ts:42–74`). Inside the read transaction, `lockAndRecheckStaffSessionContext` takes the User security boundary and locks/rechecks the exact session ID, User ID, token hash, creation generation, revocation and both expiry clocks (`staff-session-revalidation.ts:11–36`; `staff-user-security-lock.ts:8–17`). A prior context, session ID or source UUID is never a capability.
2. Authorize by source scope. Location-scoped categories require the current active Organization, exact selected active Location, role, `DASHBOARD_ACCESS` entitlement and exact `membership_location_access` grant where applicable. ALT-15 requires current active Company Admin membership and owning Organization directly, protected MFA and Dashboard entitlement; it must work with no selected Location and must not derive authority from a selected Location. The LM path for Location sources takes the shared `staff-management-org` advisory fence and rechecks after the grant writer, requiring `READ COMMITTED`; the CA Organization path uses protected management/MFA and Organization locks. Alert reads set `recordActivity: false`, so polling and Seen do not extend CA idle assurance (`management-alert-audience-authorization.ts:33–51`; `dashboard-read-authorization.ts:41–108`; `dashboard-location-authorization.ts:38–68`; `management-authorization.ts:100–166`).
3. Each owning source repeats current session/scope authorization and its own permission before candidate selection, count, overflow, correlation or exact detail. Location sources recheck the same membership/Organization/Location tuple; ALT-15 rechecks the active Company Admin membership and Organization without a Location predicate. Custody, geofence, finance, Shift and staff-security readers add their own gates. Preserve DEC-108 revocation fencing and prevent stale client responses after switching scope or renewing identity.
4. CA protected assurance has an eight-hour maximum age and 30-minute inactivity window; sensitive operations add five-minute freshness (`apps/api/src/modules/auth/mfa/mfa-assurance-policy.ts:17–19,35–57`). ALT-05 explicitly uses the sensitive check; administrative ALT-13/15 source reads use the protected non-sensitive freshness check. The local MFA bypass is default OFF and throws unless `NODE_ENV === "development"` and `DATABASE_URL` resolves to a local PostgreSQL host (`local-mfa-bypass.ts:21–51`). Production configuration still needs environment attestation; a test run with bypass enabled is not security evidence.
5. Enforce source authority before any candidate, count, overflow, correlation, receipt, navigation or exact-detail probe. Preserve nondisclosing denial and `no-store` responses. The unified preview rejects unavailable sources rather than returning a false zero (`management-alert-unified-preview-query.ts:12–16`).
6. On source click, reauthorize the exact current item and episode. A prior preview, saved URL or older authorized source result never acts as a capability. Return consistent nondisclosing denial for unknown, out-of-scope, stale, unproven and revoked objects; `management-alert-preview.controller.ts:80–174` gates the routes and `management-alert-unified-detail-query.ts:47–79,205–219` checks exact identity again.

Database runtime grants include table-level `SELECT` on both alert tables (`management-alert-timing-runtime-privileges.mjs:22–25` and `management-alert-seen-runtime-privileges.mjs:11–14`); the inspected migrations do not introduce tenant row-level security. Application source/query predicates therefore remain a critical isolation boundary. A runtime role having `SELECT` is **not** evidence of tenant-safe SQL.

## URL and event-transport privacy

- The access credential is sent in the bearer `Authorization` header (`apps/dashboard/src/lib/api/dashboard-api-client.ts:134–135`); the session resolver computes and compares its hash. No access, refresh, Staff session, guest, pickup, OTP or other credential token is placed in the alert URL or query string.
- Current source navigation does place `alertCategory`, `alertSourceId` and `alertEpisodeId` selectors in the Dashboard URL (`alert-source-intent.ts:23–27,60–75`). They are opaque source/episode identifiers, **not authentication tokens** and never grant access; exact detail must perform full current authorization again. The dialog clears these selectors from browser history on close (`alert-exact-source-dialog.tsx:111–114`). Treat selectors as operationally sensitive in logs/referrers and never substitute a reusable secret or bearer credential there.
- Those selectors identify the source occurrence; they do not yet resolve a destination for every category. The current unified exact-detail query returns `valetSessionId: null` for P2/P3 (`management-alert-unified-detail-query.ts:218–219`). Do not derive a vehicle/Session route from an event UUID or make the source UUID itself a destination capability; a typed, server-resolved destination handle with fresh authorization remains a release dependency for event-backed row navigation.
- No server-side alert SSE/WebSocket, PostgreSQL `LISTEN/NOTIFY` subscriber or alert event fan-out is implemented in the inspected source (`REALTIME_ARCHITECTURE_DECISION.md:21–24`). The current Dashboard still uses 60-second foreground polling; that does not satisfy Issue #432's healthy-QA three-second delivery target. The only current alert-adjacent `BroadcastChannel` is the same-origin personal timing-change hint; it carries the Organization ID only, not preference values, source events, counts, source IDs or credentials (`alert-timing-changes.ts:1–28`). It is a local invalidation hint, never authority.
- If a future realtime transport is separately approved, browser messages must contain only an invalidation envelope such as `{type: 'invalidate', scopeVersion, sequenceHint?}`. Do not broadcast titles, counts, source/episode IDs, vehicle/person/location facts, GPS, Seen state, preference values, audit/payment payloads or tokens. Any Organization/Location routing identifiers belong only in bounded internal replica routing, never in the browser message. Use transaction-coupled notification so rollback emits nothing; the browser must fetch a fresh source-authorized preview after every hint/reconnect. Route ALT-15 by owning Organization to current protected CA streams across selected Locations and with no Location selected; the subsequent preview must use the same Organization authority. Never route it by a fabricated Location. ALT-17 must remain outside ordinary bell/stream fan-out and inside its authorized subscription-only utility (`REALTIME_ARCHITECTURE_DECISION.md:37–52,68–73`).

## Data minimization and audit

- Return only bounded category/title/severity/source time and minimal scoped navigation identifiers. Never include customer tokens, pickup/OTP/QR codes, private verification metadata, takeover reasons, GPS coordinates/routes, private key custody history, provider references, payer details, raw audit metadata, secret credentials or identity-inference fields. DEC-110 lines 14–18 and DEC-111 lines 14–17 are stricter than generic Dashboard read access.
- Personal timing storage is one typed `(organization_id,user_id)` record; a GET defaults revision zero without creating rows. Own-user full-value PUT must validate six integer ranges and expected revision, reauthorize inside the transaction, perform one CAS change plus one **minimal** management audit, and handle exact retries as no-op. Changed CA PUT requires sensitive five-minute MFA; LM follows its existing grant/assurance contract (DEC-109 lines 40–50). `management-alert-timing-authority.ts:20–67` implements the scoped boundary; `management-alert-timing-repository.ts` holds the guarded persistence and audit.
- Only `ALT-05/07/09/13/15` committed **occurrences** are intended to support explicit user-click Seen; only a server-confirmed write changes the receipt. The unique `(Organization, User, category, source occurrence)` key and insert-only repository preserve idempotent replay; no bulk mark-on-open or source-domain change. ALT-15 Seen must reauthorize current CA membership and owning Organization independently of selected Location. The receipt query checks source existence and the seven-day window before returning an existing receipt (`management-alert-seen-command.ts:19–53`; `management-alert-seen-repository.ts:20–66`).
- **P1 — ALT-13 Location Manager Seen is weaker than source read.** The ALT-13 list/detail reader calls `authorizeForceEndedShiftAlert` → `requireSourceRole`, which rechecks protected session/MFA and exact LM Shift/Location authority (`administrative-occurrence-authority.ts:112–128,181–211`). The ALT-13 LM Seen path currently checks Dashboard scope/role but does not call that protected source authority or `requireProtectedReadSession` (`management-alert-seen-authorization.ts:27–48,81–92`); a Location Manager can therefore reach Seen without the protected MFA assurance required to read the occurrence. Align the Seen path with the exact source reader authority before enabling ALT-13 Seen.
- **P1 — ALT-15 normal bell scope still depends on selected Location.** The accepted contract is CA-only and Organization-scoped (`audit_events.location_id IS NULL`), independent of selected Location. The inspected v1 preview/Seen path is Location-scoped and still requires active selected-Location context. Add a separately authorized Organization-scoped normal-bell preview and ALT-15 Seen path that rechecks active Company Admin membership, Organization, entitlement, audit capability and protected MFA without Location grant/selection; keep ALT-15 unavailable through a Location-only route until then.
- **P1 — ALT-17 must be rejected at every generic ordinary-bell boundary.** The current unified controller rejects ALT-17 and the category matrix restricts it to the CA subscription utility, but the shared generic category/decoder/correlator path can still accept an ALT-17-shaped candidate with `locationId:null` at an intermediate boundary. No current caller emits such a candidate; that does not make the shared contract safe. Add explicit ALT-17 rejection to the ordinary-bell schemas, response decoder, correlator and fan-out boundary, and test both null/non-null Location plus CA/LM roles. Keep the existing subscription-only restriction path separate.
- **P2 — ALT-15 Seen uses a different named capability guard.** ALT-15 list/detail names `TENANT_AUDIT_READ_ELIGIBLE`, while Seen names `STAFF_MANAGE_ELIGIBLE` and performs its own constrained Organization-event lookup (`administrative-occurrence-authority.ts:112–128,150–177,214–221`; `management-alert-seen-authorization.ts:81–92`; `management-alert-seen-source.ts:129–152`). Both names are currently entries in the static `companyAdminManagementCapabilities` allowlist, and both paths require CA, `DASHBOARD_ACCESS`, owning Organization and protected MFA; this is code-contract drift, **not evidence of a current dynamic entitlement bypass**. Prefer one shared ALT-15 source authorizer or explicit equivalence tests before changing the capability model.
- **P1 — exact seven-day boundary mismatch blocks Seen acceptance.** Occurrence list readers include equality with `event_time >= statement_timestamp() - INTERVAL '7 days'` (e.g. `staff-security-occurrence-reader.ts:53–54`, `force-ended-shift-occurrence-reader.ts:48–49`); Seen insertion/retry requires `clock_timestamp() < occurredAt + INTERVAL '7 days'` (`management-alert-seen-repository.ts:45–60`), while the DTO currently marks occurrences Seen-eligible. At exact equality a row can still be listed as Seen-eligible but the PUT rejects it. DEC-110 does not settle equality. Record one accepted inclusive/exclusive boundary, align every reader, `seenEligible` projection and Seen insert/retry, then prove boundary−1ms/equality/+1ms with the same PG17 clock.
- Alert GETs create no audit or operation event. Only an actually changed preference PUT emits `MANAGEMENT_ALERT_TIMING_PREFERENCES_CHANGED` containing actor, own-user target, changed-key **names**, revision before/after; never field values (DEC-109 lines 44–50).

## Prototype controls and acceptance gates

The #432 prototype must explicitly label data as synthetic, model CA/LM/denied-role views, distinct selected Locations, ALT-15 with no selected Location and across Location switches, a revoked entitlement/grant, an expired/revoked session, an empty source vs unavailable source, unproven timestamps, repeated Seen click and an active-not-Seen case. UI-02 may open a local synthetic destination preview using fixture data and the fixed fragment `#SIM-TARGET-INCIDENT-1042`; assert only that fragment changes/restores and that production pathname/query and network remain unchanged. Assert that ALT-17 never appears in the ordinary bell; the existing `/billing-subscription` subscription utility remains unchanged and is outside this bell prototype. UI controls may simulate API-denied outcomes but must not call production alert, custody, staff, Shift or payment APIs, or imply that screenshots prove tenant isolation.

Before any **separately authorized** real rollout, require independently reviewed real PostgreSQL 17 tests with MFA bypass OFF: cross-tenant and cross-Location negatives, role/entitlement/MFA revocation during read/Seen, source-specific information minimization, same-user concurrent Seen and unknown commit, preference CAS/audit rollback, stage/Payment provenance, count/overflow after correlation, bounded SQL plans and mounted bearer HTTP/browser tests. `docs/validation/issue414/W7_HTTP_FOREGROUND_CADENCE_HARNESS.md:1–28` records a real local Phase-1 simulated-tabs run, **not** full P2/P3 or production certification. Source state on this review SHA is not itself an executed security gate.

## 1. Typed manifest contract and evidence semantics

Every row below specifies this proposed review type; fields are deliberately closed rather than an arbitrary authority JSON object:

```text
U2Writer {
  id: stable review identifier;
  kind: AUTH_CEREMONY | MANAGEMENT_AUTHORITY | OPERATOR_AUTHORITY |
        SESSION_BOUND_PUSH | MAINTENANCE | SQL_DEFINER | FIXTURE_ONLY |
        EXTERNAL_UNKNOWN;
  currentEntrypoint: source path + function, including direct SQL invokers;
  effect: exact protected DML and downstream trigger/worker effects;
  sourceAuthority: credential actually presented and genuinely verified,
                   or trusted operator/fixture boundary, never raw actor IDs;
  orgAndSubject: actual current org, User, membership, session, grant scope;
  currentLocks: acquisition sequence *observed in source* (no assumed join order);
  grants: provisioner-declared runtime column/table rights or function EXECUTE;
  proposed: purpose-specific genuine ceremony + locked-state predicate +
            typed command/payload digest/receipt + proof issuance eligibility;
  retryAndUnknown: first, replay, concurrent, conflict, state advanced,
                   changed payload, COMMIT-unknown and secret-disclosure policy;
  retirement: exact old DML/EXECUTE and caller/provisioner/worker obligations;
  verification: focused positive/negative, PG17 two-connection and ACL tests;
  state: SOURCE_VERIFIED | PROPOSED_ONLY | EXTERNAL_UNVERIFIED;
}
```

`SOURCE_VERIFIED` means a named repository code path/SQL statement or a *provisioner-declared* ACL. It does **not** mean the effective permissions of a deployed role were measured. `PROPOSED_ONLY` never represents an implemented proof function or accepted lock migration. `EXTERNAL_UNVERIFIED` means the writer, inherited role, deployment copy, operation authority or execution may exist outside the reviewed source graph; absence of a repository endpoint is not proof of absence. A raw SQL `FOR UPDATE OF a,b` and an unordered bulk `UPDATE` cannot establish a physical row acquisition order. Run all future acceptance tests using an independently attested disposable PostgreSQL 17 instance and fresh runtime, privileged maintenance, PUBLIC and inherited-role principals.

**Source shorthand:** `A(name,key)` = transaction advisory exclusive; `S`/`X` = row `FOR SHARE` / `FOR UPDATE`; `R` = unlocked read; `W` = DML and its implicit row lock; `T` = immutable transactional append. `U` = User; `SS` = `staff_auth_sessions`; `RC` = `staff_refresh_credentials`; `F` = `user_mfa_totp_factors`; `C` = `mfa_recovery_codes`; `M` = `organization_memberships`; `G` = `membership_location_access`; `O` = `organizations`; `E` = `organization_subscriptions`; `L` = `locations`; `I` = `staff_onboarding_invitations`; `P` = `staff_push_registrations`; `PD` = `staff_push_deliveries`. Shared objects such as AuditEvent, account-security audit and durable anti-abuse events are separately named when they matter. These abbreviations describe actual tables, not new schema objects.

## 2. Genuine session/authentication writers (typed rows A01–A11)

Each proposed command is **unimplemented**. A signing service must accept only in-process, genuinely verified credentials/ceremonies and a purpose-specific, schema-validated canonical payload; no endpoint, SQL-accessible hash/session ID, diagnostic method, local MFA bypass, fixture, or general-purpose signer may mint a `vap1` proof. The signer must bind exact backend/full transaction ID, one-use challenge, deployment audience, key ID, operation/purpose, actor, User/session, organization/target where relevant, credential/factor version, expected generations and SHA-256 of the *entire* closed payload. SQL must verify MAC plus fresh persisted state under compatible locks and atomically consume challenge+append receipt+business/audit mutation. This describes U2's candidate acceptance shape, **not** an endorsed cryptographic mechanism; U1 is open.

### Onboarding reservation and dual-lease ordering (M04/M05 — PROPOSED)

Current `staff-onboarding.service.ts:create/resend` calls
`reserveFreshOperation` after taking the outer email/User/management locks;
`antiAbuse.reserve()` takes a *separate* pool lease and advisory lock. The
replacement must perform durable purpose/actor/target/Organization-bound quota
reservation on a short, completed lease **before** any domain lock, using
bounded read-only discovery. It must bind the returned reservation identity to
M04/M05's immutable operation fingerprint, then fully reauthorize and lock the
real actor/target state inside the protected command. Never acquire a second
pool lease while the domain transaction owns locks. Finalize the reservation
only after releasing the domain lease: COUNTED for a committed **changed**
invitation issuance, IGNORED for an authorized unchanged same-operation linkless
replay; confirmed rollback and unknown COMMIT have distinct durable outcomes.
Unknown COMMIT requires a fresh
lease/receipt reconciliation before setting `IGNORED`; a network exception
cannot prove rollback. Negative tests exercise a constrained two-connection
pool, an exhausted second lease, failed quota finalization, mismatched operation
ID, transport loss during COMMIT, rollback and simultaneous create/resend.
This does not change accepted quotas or make an abuse reservation issuer proof.

## 8. Strict U2 typed purpose contracts — final proposed authoring specification

**PROPOSED, NOT IMPLEMENTED.** Each WRITE suffix X defined below (including independently discovered transitive **X01** in §8.3a) maps to candidate PostgreSQL signatures public.vap1_prepare_X(p_operation_id uuid, p_request public.vap1_X_request_v1) RETURNS public.vap1_challenge_v1 and public.vap1_execute_X(p_proof_bytes bytea, p_mac bytea, p_payload public.vap1_X_payload_v1) RETURNS public.vap1_result_v1. **Exception:** A04-resume is an authenticated disclosure-only variant whose `vap1_execute_mfa_enroll_resume` returns the closed `public.vap1_mfa_enroll_resume_result_v1` with existing encrypted envelope solely after full proof and same-session gate; it never uses a generic nonsecret result to smuggle ciphertext into a receipt. Proof frame bytes and 32-byte MAC are **distinct** parameters under S1. Each request composite contains only purpose-specific discovery selectors; prepare derives subject, actor and scope from persisted rows. Each payload is a distinct CREATE TYPE composite with exactly its row's fields plus mandatory schema_version SMALLINT = 1 and operation_id UUID. No generic JSON authority object, generic UPDATE opcode or externally selectable signer. The exact CREATE TYPE definitions, private command result enum and installed SQL signature list are still **UNIMPLEMENTED engineering gates**, not existing code.

Field notation: u = UUID; i = INTEGER (nonnegative checked); n = BIGINT; b = BOOLEAN; t = bounded/allowlisted TEXT; ts = TIMESTAMPTZ; h = TEXT with full source-versioned purpose-specific SHA-256 verifier prefix and 64 lowercase hex characters; d = BYTEA exactly 32 bytes of a canonical nonsecret digest; ids = sorted/distinct UUID[]; role = public.membership_role; status = public.membership_status. A question mark after a field makes that single field SQL NULL-able; all others are required, never implicit. Typed arrays must have a declared composite row shape, bounded length and deterministic ordering. Unknown fields, empty hashes, wrong digest prefix, duplicates, wrong scope, wrong version and invalid enums deny admission. Raw passwords, bearer tokens, TOTP and recovery codes are never SQL parameters.

**S1 canonical wire alignment (read-only cross-check of integrated Prime S1):** candidate command payload = TLV frame kind 0x01, protected locked state = frame kind 0x03, proof = frame kind 0x02. Each frame begins ASCII VAYLET/VAP1, a zero byte, kind U8, schema U16BE=1, field count U16BE, then ascending field ID U16BE, wire type U8, length U32BE and exact bytes. An app-side trusted branch independently re-encodes the exact request after observing actual submitted password/refresh/access/TOTP/recovery/invite/reset credential possession and verified immutable version; it must not blindly HMAC SQL-returned bytes. A SQL-readable hash, actor UUID, fake auth flag, local MFA bypass, fixture or signed snapshot cannot authorize signing. Operator ceremonies require separately attested non-runtime authority. **Schema rule:** The ordinary runtime principal needs USAGE on the **public callable command schema**, and EXECUTE on only named purpose-specific prepare/execute signatures. A callable function placed in a denied private schema would be unusable to the legitimate client; explicitly separate callable/public from private storage/lookup symbols. New private owner is proposed NOLOGIN, NOINHERIT, non-superuser, with immutable reviewed search_path and all table/helper references qualified. Revoke PUBLIC on each new function and verify no default function privileges restore it. Keep required public composite TYPE USAGE only where necessary for narrow commands; protect private type/helper and key material.

**SQL HMAC gap:** S1 specifies the PostgreSQL 17 candidate pgcrypto-provided hmac(data bytea, key bytea, text) with SHA-256, digest and a 32-byte SQL-side CSPRNG (possibly gen_random_bytes). **No pgcrypto extension installation is declared by repository migrations, and no deployed extension version, installation schema, SQL pg_proc function signature/EXECUTE privilege or key-injection confidentiality was checked.** The extension's installed namespace cannot be assumed to be literally named pgcrypto. This is a privileged release-owner/DB security review gate: install/verify the exact function schema under attested extension-owner custody, limit CREATE/ALTER EXTENSION, qualify function lookups, test no runtime key table SELECT or free-form verifier oracle, and validate server/proxy/driver/error/audit/query-stat logging using synthetic canaries. Public HMAC EXECUTE alone is not proof of key exposure if the SQL-only role cannot read/select key material, but SQL key storage without proven encrypted-at-rest and log-safe delivery remains a U1 blocker. Do not assume pgcrypto is available or switch to a different cryptosystem silently.

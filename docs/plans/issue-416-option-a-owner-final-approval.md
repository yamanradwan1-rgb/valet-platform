## Architecture and assurance verdict

**Target trust chain:** original submitted password / opaque refresh / TOTP / recovery code / invitation → genuine, context-specific application verification → current protected session/credential/factor and admitted legacy authority → app-only purpose-specific signer → one-transaction, one-use typed challenge / `vap1` proof → ordinary runtime role may call **only** matching narrow `SECURITY DEFINER` command → SQL revalidates current User, session, Organization, membership, grants, entitlement, factor, expected versions, key, proof clock and digest under approved ordered locks → atomic state mutation, immutable receipt and security audit → commit, bounded error, authorized nonsecret replay or unknown-COMMIT reconciliation.

**The attacker boundary is intentionally limited:** possession of the ordinary application **database role** or ability to read SQL-visible session hashes/actor IDs must not mint password verification, accepted MFA, a staff session, management authority, factor evidence or a valid signed proof. The genuine server authentication path and protected signer/key remain trusted components; compromise of the API execution identity, migration/`SECURITY DEFINER` owner, encryption root or privileged operators is a different, separately managed threat. An unverified server-side boolean, forged `StaffSessionContext`, client actor ID, GUC, arbitrary JSON command, reusable SQL hash, prior-v9 session or stale receipt must **never** substitute for the original ceremony. There is **no current implementation** of this protected command boundary.

**Decision recommendation:** complete a reviewed source-level contract now and require separate external production-capability attestation before release or claiming implementation readiness. The effective key storage, verifier availability, deployed SQL roles, backup/restore and all operator identities are **EXTERNAL — NOT VERIFIED**. Static documentation review cannot prove SQL-only forgery resistance or deadlock freedom.

Ordinary SQL runtime authority must be unable to create accepted identity, MFA evidence or authority by changing stored facts or calling legacy `SECURITY DEFINER` entrypoints. Migrate all dependent legitimate writers and privilege provisioners before retiring the old DML/EXECUTE grants. The v9 raw bearer in SQL and retained authority-changing direct runtime column grants are superseded **internally** by this protected proof protocol; all v9 external reset, Staff Login/Refresh/MFA, Web/Native, notification/audit and security requirements remain unchanged.

**Authorizes:** a future reviewed implementation proposal of purpose-specific typed command functions, private one-use challenge/receipt, signer boundaries and coordinated grants migration **after separate implementation authorization**. **Does not authorize:** current code edits, user-facing reset changes, general-purpose SQL signing endpoint, secret exposure, production privilege changes or deployment.

**Why and evidence:** the [U2 inventory](issue-416-option-a-writer-inventory.md) and real source `packages/database/scripts/mfa-runtime-privileges.mjs`, `staff-management-runtime-privileges.mjs`, `staff-onboarding-runtime-privileges.mjs` show current SQL paths with sensitive direct writes or actor-ID-only callable definers. Additional independently identified `staff_shift_force_end` accepts a runtime SQL-readable access-hash and remains callable with existing `shift-force-end-runtime-privileges.mjs`; the future **X01** writer and nested provisioner must be migrated or C6 blocked. The existing generic runtime `append_runtime_account_security_audit_event` also permits falsified MFA ceremony audit events (four source-defined MFA names) even though migration 112 reserves reset events: the future forward-only security migration must protect the MFA event types as well, retaining migration 112 unchanged. Current `anti_abuse_events.UPDATE(state,group_key_hash)` can discount COUNTED/PENDING attempts to IGNORED from a compromised runtime SQL role; narrow protected limiter transitions, **atomic four-scope R02 reservation bundles**, and SQL-only denial tests are now part of the S1/U2 cutover contract. Original Issue #416 v9 §A.E permitted narrower direct grants and raw bearer SQL under a production log-confidentiality gate; Option A intentionally changes that **internal** decision. DEC-023/024/072/078/080/081 remain binding for identity, durable rate limits, replay, assurance, roles and Company scope.

**Security impact:** closes a SQL-only credential/MFA/authority forgery route **only after** every weak writer and old provisioner is fenced; unsigned/runtime-supplied claims never authorize signing. **Operational impact:** broad synchronized auth, Management, Push and operator writer migration, live role/overload checks, compatibility with Web and Native and a drained release window. **Acceptance tests:** SQL-only direct INSERT/UPDATE/DELETE and old EXECUTE negative matrix; fake session/hash/role/TOTP/signing oracle; true password/refresh/TOTP/authorization positive cases; consumed refresh replay commits family revoke then fails; pending MFA same-session seed replay; copy-once secrets; tenant/role/entitlement races; unknown COMMIT. **Rollback:** only a proof-aware N/R binary+schema/ACL, never restore v9 raw bearer or weak direct grants. **Blocked:** proof issuer, protected DDL, privileges and #416 reset implementation until approved and production capability proven.

## U1 — Select one concrete key custody mechanism

**Recommended explicit approval question and text:**

> May VAYLET use a dedicated independent **256-bit HMAC-SHA-256 per-environment/per-audience `vap1` signing key**, delivered to the API by an **attested production secret-injection channel**, and provision its matching verifier key **once through an authenticated, audited, offline migration/security-custodian session** into a private PostgreSQL key registry owned by a non-login `SECURITY DEFINER` security owner? Ordinary runtime SQL receives narrow command EXECUTE only, with **no** key-table SELECT, owner membership, impersonation or general verifier helper. This approval is **conditional** on the deployment owner proving encrypted PostgreSQL at-rest storage and separately encrypted, access-restricted backups, protected injection and telemetry, PostgreSQL HMAC verification support, named custodian/operators and a tested rotation/retirement/restore boundary. If those facilities are absent or the verifier key is SQL-runtime readable, the mechanism is **not approved for implementation/release** and an independently reviewed in-Option-A verifier alternative is required.

**Actual repository mechanism:** current API secrets are read from environment configuration; production `DATABASE_URL` uses one restricted pool and `MIGRATION_DATABASE_URL` is forbidden inside the API by DEC-025. A controlled DB migration/provisioning boundary exists. There is **no proven production secret manager, encrypted DB volume, encrypted backup, specific key-delivery service, ready `pgcrypto` extension, secure SQL HMAC verifier or named operator**. Local compose PostgreSQL 17 and checked-off templates are not deployment attestation. No separate privileged runtime pool is proposed. See [U1 source-evidence table](issue-416-option-a-key-custody.md).

**Operating roles:** VAYLET security custodian generates/escrows the secret and maintains immutable key ID/audience registry; controlled database release operator provisions verifier via secure one-time path; independently authorized release approver confirms effective ACLs, key lifecycle and N/R readiness; deployment owner attests production injection, encryption and restore; on-call security operator owns emergency ingress/drain and retirement. These are **role descriptions**, not a claim that the people, credentials or toolchain already exist.

**Required gate before implementation acceptance:** deployment owner produces a nonsecret description of the actual API replicas/runtime identity, injection channel, DB encryption boundary, managed at-rest protection and backup encryption/restore; DBA proves HMAC verifier availability/version under approved PG17 extension policy, protected definer ownership and no runtime/PUBLIC/inherited key access; security operator demonstrates synthetic key canaries absent from PostgreSQL statement/parameter/error/proxy logs, `pg_stat_activity`, tracing, crash dumps and CI; operator rehearses key promotion epoch and `FOR SHARE`/`FOR UPDATE` COMMIT retirement barrier, stale signer, unknown key and older-backup restore with immutable retirement checkpoint. **FAIL CLOSED** on missing/mismatched key, stale replica, unsupported crypto, log disclosure or absent independent recovery material. **No secret material** in migrations, function source, GUCs, logs or ordinary SQL-readable state.

**Security impact:** HMAC is symmetric: anyone obtaining the verifier key can sign; private ACL alone is insufficient for disk/backup/operator confidentiality. **Operational impact:** custodian/recovery roles, encrypted backups, restart/readiness, staged key overlap and potential outage; cost/operator capacity must be validated. **Rollback:** never unretire an old key; N/R must share current key/epoch and verified admission registry. **Blocked:** storage/verification implementation and any production claims until external attestation is recorded.

If compatible R is unavailable, **do not proceed** unless a separate explicit secure-outage/fix-forward approval, with measured RPO/RTO and operational continuity, is obtained.

**Authorizes:** detailed planning and future review of the C0–C6 release contract **only**. **Does not authorize:** this task executing backup, session/key/role rotation, SQL migration, cutover, actual outage or deployment.

**Evidence:** existing `provision-runtime-role.mjs` can recreate sensitive grants, real production deployment and backup topology are not represented in repository configuration, and reusing an old snapshot could revive spent codes, revoked sessions, factor steps, token generations or membership/entitlement authority. **Security impact:** forbids mixed-version bypass and unsafe privilege restoration; respects session, MFA and key retirement barriers. **Operational impact:** authentication interruption and planned re-login, customer operations staff communications, staffing for mediated identity recovery, verified RPO/RTO and backup/restore capacity. No downtime, RPO or RTO number is inferable from source; deployment owner must measure actual drain/pool completion times, backup restore duration, affected account count, operator case throughput, compatible R rehearsal and recovery point lag before release scheduling. **Tests:** N→R→N, twice new provisioner, denied historical credential+old runner **before C6**, effective PUBLIC/inherited role ACL, stale replica, older-backup revival, every C/R/D/U PG17 race, accepted refresh/MFA replay behavior, zero secret sinks and startup refusal on ACL drift. **Rollback:** after C3, use only compatible R or approved secure outage/fix-forward; never unretire keys or reinstall old grants. **Blocked:** production release and any cutover authorization until fresh external evidence and a separate execution directive.

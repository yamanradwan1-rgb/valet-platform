## 1. Executive Summary

Production OCR is deliberately unavailable: `PlateOcrCostGuard.acquire()` permits only development/test, before provider I/O. Valid HTTPS provider configuration does not bypass it. This is DEC-074 §22.3 safety behavior, not proof of a provider outage. HTTP operation `SUCCESS` does not imply OCR `MATCH`.

The owner-selected architecture remains **PostgreSQL Lean A + S**, with one combined current-authority/Admission transaction and no precautionary second auth transaction. OD-18 delegates schema, indexes, locks, internal contracts and maintenance details to engineering; §§10–15 now recommend concrete defaults from the inspected repository. They are proposed future implementation design, not existing code or formal repository DEC amendments. Nonzero launch values/provider facts are not prerequisites for designing a safely disabled implementation.

Preserve authoritative `Organization + Membership + target Location`, identity limits of one concurrent call, 5/10 seconds and 20/60 seconds; add only global and Organization lookup quotas, explicit OFF/kill controls and minimal owned recovery state. Fail closed on shared-store failure. Never automatically repeat a potentially billable HTTP request, refund uncertain consumption, or recycle remote exposure on TTL alone. Keep manual intake independent of OCR. One successfully committed Admission consumes one conservative integer lookup unit from platform and Organization allocations, retained for every later outcome, including proven no-send; this selected accounting policy is not a vendor invoice claim.

The second workstream replaces timed scanning with **employee-triggered Capture**. Camera opening/readiness only presents preview. One explicit press owns one bounded camera/ROI operation and at most one OCR HTTP attempt; failure may produce zero requests. There is no 1.2-second capture timer, five-attempt automatic cycle, or automatic NO_MATCH retry in the desired final workflow. After a current, safely completed NO_MATCH, prefer retaining the same live preview and re-enabling the same Capture button after cleanup, without reopen/remount or automatic retry. Focused source review in §16 identifies a small compatible change; runtime/device proof is still due. Preserve editable Confirm Plate, explicit human Confirm, exact returning recognition, Manual Plate and No Plate.

Strict visual freeze: the sole additive visual control is one existing-style `CheckInButton` (wrapping `EmployeeButton`). Only its localized label and minimally necessary truthful scanner guidance may change. Preserve the 260px viewport, ROI, Torch, tokens, header, existing controls and other screens. The owner provisionally accepts Capture after preview guidance and before Manual Entry. A separately authorized implementation may insert it without a design-exploration or pre-implementation screenshot gate. Real before/after device evidence must pass the visual freeze before acceptance/merge; failed evidence blocks merge, not planning.

Keep backend Issue #429 and Native implementation separately owned, reviewed and rolled back. Recommend a separately linked Native issue and separate implementation branches/reviews; create neither here. The original security research on tenant isolation, remote uncertainty, TLS/egress, restore-lost usage and least privilege is retained. Unused quota expires with **No Rollover**; old remote exposure stays protected across boundaries. Recovery never synchronously blocks normal Check-In, and only authenticated VAYLET platform operators control quotas/kill/recovery with immutable provenance. Ordinary Check-In must show **no statistically credible latency regression** before merge; the earlier percentage tolerance is superseded. Additionally, avoidable `NOWAIT` denials despite budget/concurrency headroom require an independent pre-merge availability gate; fast rejection is not OCR success. The plan is substantially complete: separately authorized docs-first Phase 0 precedes separate Backend and Native implementation. Extensive billing infrastructure, extra quota tiers and generic limiter platform stay deferred.

## 4. Current Backend Architecture and Existing Implementation Patterns

### Existing implementation patterns

Evidence E01–E13/E16–E21 in §34 proves current behavior/capability, not acceptance of new policy:

1. `PlateOcrAuthGuard` authenticates before bounded multipart allocation, sets no-store, and carries only `plateOcrUserId`. The principal resolver checks persisted session expiry/revocation and active User but drops exact session context from its returned principal.
2. `PlateOcrController` validates strict metadata/country, JPEG MIME, ≤1 MiB, buffer-size agreement and SOI/EOI markers; zeros the received buffer in `finally`. Signature checks are not a complete JPEG decode.
3. `PlateOcrService.recognize()` opens a PostgreSQL transaction, calls exported `authorizeCheckInLocation(..., true)`, locks exact-Location Shift eligibility and reads `COALESCE(location override, Organization default)`. It commits/releases before local cost admission and provider I/O.
4. `PlateOcrCostGuard` uses a bounded process-local map (default 1,024 identities), one in flight and exact 10s/60s timestamp histories. Non-development/test modes deny. Replicas/restarts do not share state.
5. `PlateRecognizerSnapshotProvider` performs one multipart POST with redirects rejected, HTTPS in production, default 4s timeout (allowed 100–10,000ms), 64 KiB response cap, at most 100 candidates and deterministic threshold/tie-break selection. No paid-provider retry exists.
6. `PlateOcrProvider.recognize()` exposes only the neutral response. It does not expose non-sensitive readiness, dispatch/completion certainty, cancellation from caller, or billing evidence; §15 identifies this internal abstraction gap.
7. `management-integrations-status.ts` independently maps configured production OCR to UNAVAILABLE from NODE_ENV. Future truthful readiness must remove that redundant inference under approved integration semantics, without a Dashboard redesign or paid probe.

`CheckInModule` imports Auth, ConditionPhotoAdmission, RuntimeDatabase and HttpInfrastructure modules; wires feature providers, the guard and provider factory, operation runner and per-controller RequestId middleware. Preserve this composition and explicit transaction/executor conventions; do not add a generic controller/service/repository stack. `complete-check-in-command.ts` is the nearest command/transaction reference.

Literal routes verified: PlateOcrController and StaffCheckInController use `@Controller("v1/staff/check-in")`; ShiftController uses `@Controller("v1/staff/shifts")`. Preserve `POST /v1/staff/check-in/plate-ocr`, HTTP 200 for valid neutral results, existing auth/input error mappings, no-store and request-ID behavior. No new public route is proposed.

`AntiAbuseService` has real transaction-aware count/reserve/finalize methods, but fixed 15-minute windows, a closed non-OCR scope union and no owned remote concurrency or global/tenant budget model. Its PENDING event is counted use, not an HTTP lease. ConditionPhotoAdmission demonstrates all-or-none checks in one transaction but disclaims being a lease limiter. Reuse patterns, not unrelated scope meanings or photo grants. The custody audit writer requires ValetSession/Vehicle scope and cannot emit standalone OCR control history unchanged.

The existing bounded PG pool is shared infrastructure. `inPostgresTransaction` detects uncertain COMMIT and discards unusable connections. No extra OCR pool/singleton is justified. Production capacity settings are mandatory; fixed pool acquisition/lock/statement budgets are 2s/2s/3s, with 5s transaction/6s operation defaults for bounded paths; general lease budgets are validated deployment values. These ceilings are not acceptable routine OCR latency targets. Inspect the actual operation scope and lease configuration during implementation rather than assuming all routes use identical deadlines.

## 5. Current Native Camera Flow

`NativeCaptureStep` renders `NativePlateCameraStep` in the existing capture presentation. `useFocusEffect` binds lifecycle and opens the controller once. Camera permission, supported picture sizes, optional picture-size remount and ROI preview metadata validation precede `controller.ready()`.

Current chain (historical/current behavior only, to replace):

```text
focus/open → permission → camera mount → ROI metadata ready
→ controller.ready(): phase preview + ocr.start(generation)
→ setTimeout(1200) → capture → recognize → cleanup
→ NO_MATCH: schedule another attempt, maximum five
→ MATCH or terminal no-read/unavailable: close and finish
```

`NativePlateOcrLoop` provides one operation across generations and no queued frames; cancellation deletes known files without waiting for an uncooperative HTTP promise. `NativePlateOcrAdapter.accept()` sets the editable draft and enters review only. `recognizeNativePlate()` uses the VAYLET API, 15s timeout, AbortSignal and auth-generation check. ## 7. Root Causes and MVP Problems

Backend: the intended shared durable admission capability is absent, so production denial is correct. Memory multiplication across replicas/restart cannot enforce total cost. Missing readiness/completion observations prevent precise internal settlement even though public results are sufficient for Native.

Native: camera readiness currently grants timed capture and up to five potential paid lookups without a distinct employee press. Owner direction removes that trigger to avoid surprise captures, unnecessary attempts and positioning friction. Manual capture reduces avoidable requests, but is not backend anti-abuse authority: a modified client can call the endpoint directly.

Planning: the original Candidate P made three transactions, dual admission/dispatch event histories and about ten persistence families the primary recommendation before showing need. It doubled authorization work and widened MVP scope. Keep its security lessons; evaluate the smaller design before paying that complexity cost. No benchmark proves either design fast enough today. Final refinement also removes the prior unnecessary NO_MATCH reopen cycle and the circular screenshot-before-placement prerequisite, while keeping safety/visual acceptance gates.

## 10. Lean PostgreSQL Architecture — Engineering Recommendation

### Minimal atomic operations

- `ocr_admit` is a feature-owned VOLATILE restricted function called inside A **after operation authority is proved**. It validates its exact persisted scope, required session/time predicates and positive configured controls; takes OCR rows in §12 order; checks active period/current DB time, budgets, active capacity and exact 5/10s + 20/60s histories; increments both spent counters and inserts one attempt atomically. Any failed write rolls back all dimensions. No per-denial row and no automatic transaction retry. Successful known commit is the admission linearization point.
- Global control `FOR UPDATE NOWAIT` serializes all admission additions, control/period changes and allocation writers. This removes the need for a separate identity-state table/advisory lock. Partial unique identity is an additional integrity barrier, not an API replay contract. Count recent identity rows after obtaining this serialization point; cap probes at configured limit+1 rather than scanning history.
- `ocr_settle` locks **only the scoped attempt**; validates owner/revision/source state; performs one guarded terminal/unknown update and, for a recovery action, required history. It never changes quota, adds active exposure or obtains Staff/Shift/global locks. Concurrent settlement can only remove exposure or mark it uncertain: admission may over-deny from an older snapshot, but cannot over-admit. Fresh admissions alone serialize active additions. This avoids making every completion contend on the global budget row.
- Operator control/provision/resolve functions (§21) are narrow, typed and separately granted. A period is staged, never automatically activated. No arbitrary table selector/dynamic SQL or generic admin endpoint.

Use READ COMMITTED and separate post-lock SQL reads inside the VOLATILE mutation function, not a STABLE cached snapshot. Prove last-unit/capacity correctness with genuine transactions and commit barriers. PostgreSQL [SELECT locking](https://www.postgresql.org/docs/17/sql-select.html), [function volatility](https://www.postgresql.org/docs/17/xfunc-volatility.html) and [isolation](https://www.postgresql.org/docs/17/transaction-iso.html) support the proposed mechanics; they are not tests or approval of this design.

### Privileges, retention and migration

Tables are private: runtime receives exact admission/settlement EXECUTE and needed scope-safe readiness only, no OCR table DML/DELETE/TRUNCATE, control changes or historical reads. Maintenance receives only bounded detection/UNKNOWN classification, never privileged resolution. Operator login receives only reviewed control/reconcile/read EXECUTE; no migration/DDL/grant authority. Functions use non-runtime owner, fixed safe `search_path=pg_catalog, public`, qualified relations, PUBLIC EXECUTE revoked, no grant option, explicit NULL/bounds/type checks. Verify owner, inherited/column/function grants and direct foreign-scope negatives.

Hot work is bounded: rate predicates inspect only the most recent 60s; execution deadlines bound live ownership; the active-state indexes bound detection by configured capacity. Keep all immutable debit/period/control history in MVP; no automatic historical deletion. Retention of legally required audit/history is not invented. Operator storage/capacity review gates provisioning each new period, so no unlimited refill or unbounded maintenance scan. Historical archive/purge is deferred until privacy/retention requirements are established; future code can safely ship disabled without a destructive cleanup job. This bounds active/query state, not mathematically finite lifetime storage; disclose growth and monitor bytes/WAL/backlog.

Before future code, synchronize focused DEC/log and schema docs, allocate new migration identifiers from then-current main, create these additive objects/functions/revokes and provision restricted roles through existing tooling. Test empty and representative data, immutable history, real ACLs and N/N-1 OFF compatibility. Roll back by shared OFF, fence/drain and fail-closed app rollback while retaining schema/debits/history and a compatible reconcile path. No historical migration edit/down migration or lost-exposure reset.

## 12. Admission and Authorization Ordering — Single Transaction A

OD-19 selects one combined current-authority/admission transaction and accepts bounded already-authorized completion in principle. No second full authorization transaction may be added as precaution. DEC-108 is response-specific and does not itself establish paid dispatch; the precise OCR extension is PROPOSED in §20 under the current owner direction. The inspected DEC-074/current service commits proof before provider I/O; no inspected source mandates a distinct B. No `SECURITY DECISION CONFLICT` was identified by this bounded source review. If an actual more-specific rule contradicts this shape, name its exact source and stop that behavior; do not silently add B or weaken it.

### Recommended A order

1. Preserve guard authentication before upload, bounded media validation and provider configuration check. Carry existing trusted `StaffSessionContext` privately instead of dropping it to only userId. Prepare multipart data before A; never call a paid health probe.
2. In A, call exported `lockAndRecheckStaffSessionContext`: Staff user-security advisory boundary → exact session row; then existing `authorizeCheckInLocation(..., true)` order: active User → Location lifecycle boundary/persisted Location → Organization settings boundary → membership → Organization/Location → explicit access. Retain exact-role, active tenant/intake and exported Shift eligibility/policy proof through debit. No fake hierarchy or client tenant authority.
3. Only after full scope authority, acquire OCR rows: platform control **FOR UPDATE NOWAIT** → Organization control NOWAIT → active global period NOWAIT → Organization allocation NOWAIT. Global serialization protects initial use and window/capacity additions; no separate identity lock. Operator budget/control writers follow the same OCR order and never then acquire domain authority locks.
4. Re-sample DB time after locks; evaluate credential access/absolute expiry and policy/Shift/time-sensitive predicates on already locked scope before decision. Validate enabled/current period/quota/capacity/windows. Scoped admission function checks persisted membership/Location/session association, not client-selected actor/Organization/account. Then both counter increments + attempt insert, and known COMMIT. Rollback/ambiguous commit permits no send. A is the only current-authority transaction, with no repeated full helper invocation after it.
5. Release DB connection; consume the private one-use current-operation permit and immediately invoke one adapter HTTP request. No queue/backoff/new SQL/refresh/retry after commit. S follows later outside all authority locks.

**Engineer-selected initial timing defaults for implementation/QA, not measured production limits:** apply the existing general DB deadline mechanism to cap A (including pool acquisition/setup) at 500ms; bound lock waits at 50ms and statements at 250ms within remaining A time, with NOWAIT for OCR hot rows. These tighten only the OCR operation, not app-wide configuration. Native/provider deadline margin still applies. Track the start of the final time-sensitive proof statement as a conservative monotonic lower bound; require fetch invocation within **250ms of that start**, and before any shorter calculated credential/period/request deadline. A slow COMMIT acknowledgement consumes this budget; do not start the age clock only after COMMIT. Fail closed if no margin. Constants are tunable by engineering only after correctness/performance evidence, never by bypassing authority.

Let `tP` be that proof-start lower bound, `tC` known COMMIT acknowledgement and `tD` one fetch invocation. Require local `tD−tP≤250ms`; interval `(tC,tD]` is immediate continuation, with no intervening work except release/currentness/age check. Provider I/O is bounded by existing timeout (default 4s, max 10s), body cap and one-fetch implementation. A GC/process pause after the last local check can still delay actual network dispatch; local age checks/SQL tokens cannot retract an already-held remote capability. The proposed OCR-specific decision expressly acknowledges that residual, requires no replay and process fencing before uncertain capacity reuse. Never claim strict remote wall-clock rate/exactly-once from a DB timestamp.

### Contention and lock proof

NOWAIT on the global OCR row returns promptly instead of holding User/Shift/access shares in a hot-row queue. Other existing authority locks still can contend; the 50ms lock and 500ms A ceilings are failure bounds, not permitted ordinary Check-In regression. If row acquisition fails, roll A back and return current safe unavailable mapping without charging/sending. SQLSTATE lock/deadlock/statement/deadline and unknown-COMMIT branches must be tested; there is no automatic DB retry. Pool acquisition uses the existing bounded pool and deadline wrapper; prove expired acquisition releases/destroys late leases correctly. No parallel private pool or silent budget enlargement. **Availability risk:** `NOWAIT` can reject an otherwise eligible employee despite adequate quota/concurrency merely because another Admission briefly holds the global control row. Treat this as a distinct internal `LOCK_BUSY` contention denial (public result stays `UNAVAILABLE`); do not misclassify it as exhausted quota or count fast denials as latency wins. Verify eligibility/headroom with a controlled independent QA oracle, not a racy later read. No automatic retry, queue or security bypass is authorized.

Settlement/maintenance never takes operational locks. S takes one attempt and can only reduce or retain exposure; global/tenant caps and identity additions serialize in A. Operator changes take OCR order only; maintenance nonblocking attempt claims never reach backward into controls. No path may hold an attempt then request Staff/Shift/global locks. Global kill or canonical revoke committing before required proof denies new admission; if A wins first, only the bounded authorized continuation applies. Logout/rotation use exact-session/security boundary; expiry is rechecked by DB time because elapsed time is not prevented by a row lock. The global/Organization policy kill does not erase already admitted work or prove remote cancellation.

## 13. Distributed Quotas, Periods and No Rollover

**LOCKED:** one successfully committed Admission consumes exactly one integer lookup unit globally and in its Organization. No automatic refund, resend, credit purchase, future borrowing or client timer retry.

### No Rollover — OD-15

## 14. Minimal UNKNOWN Recovery — Never on Ordinary Check-In

### Bounded off-path detection

Use one small feature lifecycle maintenance owner, following AntiAbuseMaintenance's lifecycle/non-overlap convention but **not** its one-second full counting cadence. The idle check can race arriving operational work, so it is resource mitigation, not proof of zero interference. §22 must compare ordinary Check-In with detection active and under backlog; skip/shorten/redesign if it produces credible regression. ## 22. Strict Check-In Performance Gate and Benchmark Design

**LOCKED OD-19/latency requirement:** no demonstrated, statistically credible latency regression in ordinary Check-In under comparable representative conditions. The prior p95 +5% / p99 +10% tolerance is superseded and must not qualify release. Additional SQL cannot be claimed mathematically free. If ordinary Check-In meaningfully worsens, the patch is **NOT eligible for merge**: optimize/redesign the bottleneck and remeasure, never lower security or mask it with average fast denials. Insufficient/noisy evidence is inconclusive and cannot certify the gate.

Structural separation: ordinary manual/complete Check-In does not query OCR cost state or wait for provider/recovery. No synchronous recovery/reconciliation, paid health probe, HTTP under DB lease, unbounded scan/queue or second auth transaction. Pool/CPU/WAL and existing shared authority locks can still transmit pressure; separation alone does not prove zero measured regression. Recovery is active in qualification, not conveniently disabled.

### NOWAIT eligible-with-headroom false-denial acceptance

Independent of ordinary Check-In latency, measure whether `FOR UPDATE NOWAIT` causes **avoidable** employee OCR denials with enough global/Organization budget, identity rolling-window allowance and provider-concurrency capacity. A quick fail-closed `UNAVAILABLE` is safe but not an acceptable *successful* scan; do not hide it by including fast denials in the allowed-request latency distribution.

Use a controlled independent quota/capacity/commit oracle rather than assuming every lock failure was eligible; include an intentionally held-row adversarial test to prove safe fast denial separately.

**Pre-merge gate:** **zero observed eligible-with-headroom `LOCK_BUSY` denials in representative approved normal and expected peak traffic**, with an adequate recorded sample and upper confidence bound (zero observed does not prove mathematical zero). Any avoidable denial or inconclusive/nonrepresentative data blocks acceptance pending optimization and rerun. Report synthetic beyond-envelope overload separately. If `NOWAIT` fails under intended traffic, compare the smallest safe contention alternative on **both** admitted OCR availability and Check-In latency; do not add unbounded waits, automatic paid retries, quota bypass or an implicit acceptable false-denial tolerance.

### Comparable experiment and statistical decision

Use owned isolated real PostgreSQL 17, production-built artifacts/restricted roles, mock HTTPS provider and blocked commercial egress.

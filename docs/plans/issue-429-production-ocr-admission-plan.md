## 1. Executive Summary

Production OCR is deliberately unavailable: PlateOcrCostGuard.acquire rejects every mode except development/test before provider I/O. HTTPS provider configuration can be valid in production without making admission permissible. This implements DEC-074 §22.3; it is not evidence of a provider outage. Operation-level SUCCESS can accompany an OCR UNAVAILABLE response.

**Recommendation, pending U-001 approval:** a focused PostgreSQL OCR admission subsystem within the existing modular monolith, using the existing bounded runtime pool and short transactions, dedicated typed budgets and reservations, exact identity rolling windows, fenced ownership and conservative usage accounting. Do not change existing AntiAbuse scope meanings. Redis is a viable alternative but has no verified existing deployment here. A provider quota plus in-memory limiter is insufficient.

Keep the existing public MATCH / NO_MATCH / UNAVAILABLE contract. Preserve the server-derived Organization + Membership + target Location identity, one concurrent authorized call, five calls per 10 seconds and twenty per 60 seconds. Keep manual/no-plate check-in and explicit human Confirm/Edit intact.

The hard part is the database/external-HTTP boundary. A committed permission to send does not prove an HTTP attempt occurred; an aborted request does not prove remote processing ended. The proposed design spends a conservative integer unit at admission and never automatically refunds ambiguous usage. It distinguishes an expiring execution lease from unresolved remote exposure. U-005 must choose the remote-concurrency recovery policy; ordinary TTL deletion cannot satisfy both strict remote exclusion and unconditional automatic recovery.

The plan is complete for owner review, **not approved for implementation or activation**. Architecture, budget values/periods, provider account facts, recovery policy, persistence/privileges, configuration ownership and privacy remain decision gates. All proposed mechanisms below are conditional alternatives or a coherent **candidate P** to approve as a whole. No proposed DEC is marked Accepted.

## 3. Problem Statement and Root Cause

Evidence E01–E05:

1. Module factory passes process.env.NODE_ENV into the process-local guard.
2. Guard line 21 returns undefined in production, staging, undefined and other non-development/test modes.
3. Service lines 74–81 maps that result to UNAVAILABLE before provider.recognize.
4. Production HTTPS config may nevertheless resolve as configured.
5. Existing guard and authenticated HTTP tests intentionally assert production fail-closed.

The missing capability is authoritative shared admission for a paid side effect. Memory resets on restart, replicas have independent maps, and there is no durable OCR global budget, tenant allocation, concurrency reservation or ambiguity ledger. Setting NODE_ENV to development or bypassing the guard would violate DEC-074 and expose paid calls without a shared ceiling.

The adapter's production-safe TLS validation and its bounded HTTP call are necessary but do not establish production readiness. Existing diagnostics distinguish provider HTTP success from match, but production boundary diagnostics currently suppress admission detail. A Management integration projection separately hard-codes production OCR UNAVAILABLE; that downstream consumer must eventually use truthful capability/readiness rather than preserve a second mode gate.

## 7. Existing Implementation Patterns

Reuse the bounded RUNTIME_POSTGRES_POOL, explicit command/executor ownership, short transaction helpers, existing auth/Location/Shift boundaries, safe operation runner and feature-owned provider adapter. Nearest examples are ConditionPhotoAdmission's all-or-none quota transaction and the complete-check-in explicit executor. The latter's audit writer is not an OCR writer.

Do not extend AntiAbuseService by pretending threshold parameters vary the window; its SQL fixes 15 minutes. Its reserve/finalize contract cannot distinguish owner generation, HTTP dispatch, expiry or vendor liability. Reusing a photo scope would couple unrelated quotas; copying photo retention/idempotency semantics is also unjustified.

IF U-001 approves candidate P, a small OCR-owned application boundary is necessary to combine several atomic constraints and represent external-call ambiguity. It belongs under check-in-api/plate-ocr-admission/, not common as a generic platform. A thin service orchestrates authorize/admit, dispatch and settle executors; provider parsing remains in the adapter. Common infrastructure never imports the OCR feature. Keep a single runtime pool/lifecycle, request-ID/filter/observer registration and existing Nest auth imports.

The internal downstream consumer is PlateOcrService, not another HTTP client. Conditional candidate capability inputs are a freshly proven Staff scope, configured provider-account alias and trusted request lifecycle; output is an opaque one-use admission handle or bounded internal denial. Settlement accepts only that owned handle and allowlisted observations. It guarantees shared accounting/authorization at admission; it does not confirm plate identity, guarantee remote cancellation, reveal budget balances or authorize later business mutation. Exact exported types/signatures remain U-010; they are not frozen here.

## 12. Recommended Architecture

**IF U-001 approves option A**, candidate P uses dedicated OCR persistence and focused executors through the existing bounded PostgreSQL pool. Its correctness rests on one authority committing global+tenant+identity admission before any paid side effect, with database-enforced tenant relationships and immutable exposure evidence. Its safety rests on fail-closed configuration/store errors, no HTTP transaction, conservative unknown-use accounting and no provider automatic retries. Its fit rests on already selected PostgreSQL, existing runtime security/provisioning and the modular-monolith scope.

Additional infrastructure: no new datastore; additive database objects, bounded recovery/cleanup invocation using existing process/worker deployment patterns, approved operator controls and existing log ingestion/alert integration. Capacity/backup/restore evidence remains required. No deployed recovery job, alert receiver or production DB capability is inferred from source.

Redis could reduce admission latency at much higher measured throughput, but introduces durability and two-store consistency risks before any demonstrated need. Option C keeps one store but broadens security-sensitive helpers without eliminating the new lease/accounting work. Candidate P intentionally favors a focused owner over a general limiter platform.

## 13. Distributed Admission Design

Everything in §§13–15 and §§19–23 describing candidate P is conditional on approval of the applicable U-items, particularly U-001/002/003/004/005/008/009. It is a concrete proposal for review, not permission to implement selected semantics.

### Candidate P lifecycle and transaction boundaries

1. Resolve Staff authentication before multipart parsing using the existing guard. Validate strict metadata, supported country, bounded JPEG signature/size and an actual current request. Keep authority-bearing fields out of the body.
2. Resolve provider configuration/readiness without any recognition or paid health probe. Missing/invalid endpoint/token/timeout is UNAVAILABLE and consumes no durable cost slot. Current provider interface hides readiness; U-010 would expose an internal non-sensitive capability, not secrets or raw provider config.
3. **Admission transaction A:** use the existing authorization path, not a client Organization. Prove active User, persisted target Location/Organization, active membership and explicit grant, employee/supervisor role, eligible exact-Location ACTIVE Shift, accepting_intake and effective OCR policy. Keep existing authority locks through the admission write.
4. Under the same transaction, read platform/provider-account and tenant controls, then take candidate P's budget/identity locks in the order below. Re-sample PostgreSQL time after waits. Verify explicit enablement, configured period and positive global/tenant quotas, identity rolling limits and live-or-uncertain concurrency.
5. Atomically insert one reservation, spend one global and tenant accounting unit, append one identity rate event and one ADMITTED usage fact. Any failure rolls the whole set back. A rejected check changes no budget or rate state. Commit successfully before exposing a usable handle.
6. **Dispatch transaction B:** with the same request context and no queue, repeat current auth/Location/Shift/policy proof and provider readiness; check request cancellation, global/tenant kill, current period and one-use owned lease. Re-sample time and check a second set of dispatch-window counters under the identity lock. Atomically transition RESERVED -> SEND_POSSIBLE and append the dispatch-permission fact. This is the last authoritative pre-send decision. Commit before HTTP.
7. After known commit, release the connection; check local cancellation/deadline again and perform **one** provider fetch. No automatic retry, redirect, task requeue or background replay. Unknown COMMIT outcome in A/B permits no outbound call by that caller. Its state may be conservatively charged.
8. Obtain sanitized internal observations (HTTP status class, timeout/network/parse category, fetch started flag and duration). Return only the shared neutral result. Distinguish a local attempt from vendor processing/billing. A result candidate never mutates identity.
9. **Settlement transaction C:** authenticate the internal owned handle, resolve its persisted scope, obtain budget/identity/reservation locks in the same order, validate state/owner/epoch, append the terminal or unknown-use fact exactly once and reconcile capacity. Do not undo the admission debit. A DB failure leaves conservative exposure persisted for recovery.
10. Clear request buffers and let Native generation/temp-file rules discard stale results. Cleanup failure must not create a second paid attempt.

A and B give precise cancellation-before-dispatch recovery and a final fresh authorization fence; two transactions add latency and conservative overcount for an admitted request that never sends. A simpler single transaction setting SEND_POSSIBLE at admission is an alternative under U-005/009, with a larger ambiguity window but fewer DB round trips. It still needs settlement and cannot refund ambiguous sends.

The accepted per-identity limits bound paid-call admission. IF U-002/005 approve P, admission and dispatch both use exact 10s/60s histories, so slow preparation cannot move a burst from one admission window into a later dispatch-permission burst. No claim is made that the database controls the exact instant a paused process writes a TCP packet. The final gate, immediate nonqueued fetch, bounded permit lifetime and no stale replay constrain normal execution; stronger remote start-time guarantees require a cooperating provider or approved egress boundary.

### Clock authority and permit-age limits

IF U-002/005/008 approve P, PostgreSQL clock_timestamp after lock acquisition owns windows, periods and leases; API/client wall clocks never reset them. Persist a last-decision floor so a backward DB-clock step cannot manufacture a fresh window or extend an old dispatch permit. A detected discontinuity/failover anomaly disables new OCR decisions pending operational review; a forward jump must not silently recycle uncertain exposure. Explicit period provisioning limits accidental period skips. Host time synchronization, tolerated discontinuity, detection and recovery are part of U-002/011 deployment approval. Tests cover backward/forward logical-clock fixtures without changing any shared clock. Exact wall-clock start-time exclusion at a remote provider remains unproven under process pauses even with DB-authoritative time.

## 14. Concurrency and Lease Model

IF U-005/008 approve P, separate three concepts:

- **Execution lease:** one process owns a reservation generation for a finite DB-time TTL.
- **Capacity/exposure:** RESERVED, SEND_POSSIBLE and REMOTE_UNKNOWN occupy the identity slot and applicable tenant/platform capacity until a safe terminal transition.
- **Accounting debit:** admission unit remains consumed for the period regardless of lease release; it is never inferred from lease liveness.

Candidate states and names below are proposed SQL values, not existing enums:

| State          | Meaning                                                                                   | Capacity                                                   | Automatic recovery allowed under P                                                     |
| -------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| RESERVED       | A committed; B has not committed; no permission to send                                   | Held                                                       | Expiry can terminalize NOT_SENT and release capacity after locked state/epoch check    |
| SEND_POSSIBLE  | B committed; zero or one fetch might occur                                                | Held even if owner expires                                 | Expiry -> REMOTE_UNKNOWN, never re-dispatch                                            |
| COMPLETED      | Recognized HTTP response/definitive adapter completion safely recorded                    | Released when remote completion interpretation is approved | Terminal; repeated settlement no-op                                                    |
| NOT_SENT       | Proven no committed permission to send, or live owner demonstrably cancelled before fetch | Released                                                   | Terminal; admission debit kept                                                         |
| REMOTE_UNKNOWN | Timeout, lost response, hard crash or uncertain send/remote completion                    | Quarantined capacity                                       | Reconcile only with approved remote-completion proof/drain policy; no automatic refund |
| RECONCILED     | Controlled evidence resolves previous unknown                                             | Depends on resolution, never a resend                      | Immutable reconciliation fact; no prior fact rewritten                                 |

State transition and billing observation are orthogonal. HTTP 403/429/5xx can be COMPLETED transport with vendor billing still UNKNOWN. A network error after fetch starts is REMOTE_UNKNOWN unless evidence proves no provider processing. A timeout's AbortController completion ends local ownership, not remote work.

Candidate TTL: **30 seconds for QA exploration only**, exceeding the current 10-second maximum provider timeout plus bounded dispatch/settlement margins. Production TTL, quarantine and reconciliation SLO are U-005; no numeric lease policy is approved. Renewal, if selected, requires matching token/epoch, live deadline, nonterminal state and a maximum total lifetime; it does not extend provider timeout or grant another dispatch. Prefer no renewal for this short synchronous call unless measured evidence requires it.

The proposed owner_token is a server-generated coordination nonce, not a Staff/provider bearer credential or independent authentication authority; it never enters public output or logs. Fence every mutation by reservation ID, full persisted scope, random owner token, monotonically increasing ownership epoch, allowed source state and DB time. A stale lease owner must not clear a successor's slot, append terminal facts or revive a terminal row. A reservation is never reassigned for another external call; recovery owns reconciliation only. The partial uniqueness boundary includes uncertain exposure, rather than a time-dependent index predicate such as lease_expires_at > now().

**Remote uncertainty trade-off:** strict one remote call per identity cannot be proved by a PostgreSQL TTL when the remote provider ignores abort or a process pauses after dispatch permission. Under P's recommended strict fail-closed alternative, unknown remote exposure remains quarantined and pages an operator. A bounded recovery procedure first disables new sends, fences/terminates old send-capable processes, establishes vendor drain/completion or a documented hard remote processing bound, then releases capacity through an audited reconciliation. If no such proof exists, keep OCR disabled for the affected scope. This is safe but has no unconditional automatic liveness guarantee.

IF U-005 instead approves finite quarantine without a remote bound, the DEC must explicitly accept possible remote overlap after the hold ends, state the exposure envelope and narrow L-003's interpretation; this plan does not silently weaken it. Alternatively use a verified compatible on-prem provider with a real enforced processing deadline/fencing interface. Redis cannot solve this remote uncertainty by itself.

Budget/rate counters and capacity persist through restart. A process death before A commit consumes none; after A commit costs one conservative unit even if no dispatch; after B commit may cost a vendor lookup. Kill switch stops new B decisions, does not erase active reservations, and attempts best-effort abort without claiming cancellation of vendor billing.

### Candidate quotas and period controls

IF U-002/003/007 approve P:

- A platform/provider-account quota caps all participating tenants, not each API instance or endpoint alias. Multiple credentials for the same billing account share its cap. An additional total-platform cap is needed if multiple accounts become enabled; one account only is the initial recommended scope.
- Per-Organization allocation caps tenant usage independently. It is not customer billing. No borrowing or implicit unlimited tenant allocation; missing/zero/invalid allocation denies.
- Preserve L-003 identity limits; do not confuse membership with User-global identity. A User with memberships in two Organizations has two identities; global and Organization caps cover aggregate spend.
- Global and tenant concurrency are positive approved integers; count both live and uncertain exposures. Add a global/provider-account short rate below the verified vendor rate to avoid aggregate 429s. These controls are new U-002 choices.
- Optional Location quotas add operating fairness but complexity/rows. Recommend defer until an approved high-traffic Location requirement demonstrates need; identity already includes Location.
- Use explicit immutable period start/end timestamps in UTC representing the verified vendor cycle. Do not assume calendar month, Location timezone or a 30-day interval. Half-open intervals [start,end); no unused-unit carry unless explicitly approved.
- Pre-provision periods and tenant allocations. At rollover use a new period ID; never reset old counters to zero. Dispatch B refuses an expired A period. Reservations never move silently into a new period.
- Carry unresolved potentially billable exposure as a conservative debit against any new period that could receive late vendor processing. Do not let period rollover or provider config rotation reset lifetime outstanding liability. U-003 must choose carry resolution rules based on actual vendor time attribution.
- A platform kill and tenant kill are independent of Company/Location OCR policy. Tenant OCR ON cannot raise platform ceilings. Shared DB state is authoritative; a local environment OFF may additionally deny, never allow.
- Configuration is versioned and server-owned; fail closed on absent or inconsistent versions. Decreasing a cap below spent usage simply denies future admission; it cannot make spent negative or rewrite records. Raising limits needs approved ownership/change history.
- Enforce maximum active identities/reservations/retained rows per allocation, bounded metadata and batch cleanup. Rejecting a quota does not allocate a durable denied row.

### Outcome charging

Under P's admission-spend alternative, MATCH, NO_MATCH, 403, 429, 500, invalid JSON/shape, timeout, cancellation, network failure, lost response, ambiguous dispatch and crash after A **all retain one admission debit**. Provider-unconfigured or denial before A commit costs zero. Proven no-send after A may be labelled NOT_SENT but does not automatically restore units. A later verified vendor credit or correction is an appended operator reconciliation; it never edits original exposure evidence or silently increases live capacity.

Provider 429 is an availability/capacity failure, not no match. Do not automatically retry it or refund it based on assumptions about charging. A documented Retry-After may guide an internal future cooldown, bounded and validated, but it cannot bypass identity/global budgets or create a retry storm.

### Exposure bound and reconciliation

For a controlled account with one fetch per admitted reservation, durable spent units S, outstanding cross-period exposure X and approved per-lookup upper cost c, controlled variable exposure is at most (S + X) × c, plus verified fixed subscription fees and applicable approved extras. If outstanding X is already included in S for the selected period, do not double-count it. A cap with conservative carried exposure keeps new admissions within Q - carried_exposure. This is a calculated bound conditional on no out-of-band account calls, no unaccounted provider fan-out, known pricing and durable non-loss of admission state. Fixed plan fees, tiers, overages, tax and calls outside VAYLET are not bounded by a naive Q×list-price formula.

Reconcile aggregate vendor usage with app debits at the same account/period/timezone: record source/date, confirmed lookup count, account calls outside this path, billable-unit rules and unresolved delta. Never assign a vendor aggregate delta to a tenant without supporting evidence. Keep verified vendor totals separate from estimated spend. Default response to unexplained excess is platform kill, preserve ledger and investigate; do not adjust counters down automatically.

### Runtime privileges and safe functions

IF U-008 approves P, prefer private tables plus narrowly granted SECURITY DEFINER admission/dispatch/settlement/recovery functions, matching the repository's feature-specific privileged mutation patterns. Functions are owned by a non-runtime migration/approved owner, have fixed safe search_path (pg_catalog, public), schema-qualified relations, explicit null/bounds checks, no dynamic SQL/table selectors, PUBLIC EXECUTE revoked, no grant option and no caller-controlled time/cleanup cutoff.

Ordinary runtime gets only exact feature function EXECUTE and any minimal approved read functions; deny broad table SELECT/DML, DELETE, TRUNCATE, DDL, ownership and private helper execution. Approved maintenance can execute only fixed bounded reconciliation/cleanup functions. Platform/tenant limit changes use separate operator privileges; runtime cannot raise quota, enable production or forge control history.

A definer function still must prove actor/tenant/Location/ownership before mutation. Reuse exported transaction-aware authorization at the application layer and duplicate/compose indispensable persisted DB predicates in the reviewed function; do not assume arbitrary actor UUID is an independent authenticated identity. Runtime role grants do not provide row-level tenant isolation automatically. Direct function tests must include foreign scope, invalid actor, stale owner, SQL NULL and attempts to choose an unrelated global/tenant account.

Existing runtime-table-privileges.mjs is 293 lines at baseline. Prefer a focused OCR privilege module plus a small composition call, not growth beyond 300. Update verification manifests/declarations if required by existing tooling. Verify pg_proc owner/security/search_path/ACL, inherited privileges, table and column grants, sequence rights and grant option; not only has_table_privilege on the table.

### Retention, cleanup and maintenance

U-008 must approve retention separately for rate events, terminal reservations, usage/control history and vendor reconciliation; no legal interval is invented. A proposed operational minimum is retain rate rows at least the longest relevant window plus clock/late-work margin, and retain reservation/debit/reconciliation records through account close and approved reconciliation horizon. Unresolved exposure never ages into reusable budget or a deleted tombstone.

IF approved, fixed cutoff, bounded batch, stable ordering and SKIP LOCKED cleanup follow existing maintenance convention; do not copy the auth one-hour deletion for accounting history. Only expired, definitively NOT_SENT or settled and retention-eligible rows may be purged/compacted; append-only cost/control evidence follows its approved archive policy. Cleanup must atomically retain the minimal tombstone/aggregate needed to prevent stale settlement/double credit; if tombstones are retired, the API has no route that can resurrect old handles. Closed-period immutable totals survive event pruning.

Recovery and deletion are separate: one reconciles orphan state; the other removes eligible old state. Each has bounded runtime and backlog telemetry. Run under one existing deployment process/worker pattern selected by U-008, no generic job broker. Multiple instances may invoke guarded batches safely; per-process non-overlap alone is not cross-instance exclusivity.

## 22. Performance and Capacity Model

All numbers here are **calculated examples or proposed benchmark criteria**, not measurements. U-002/008/011 must accept the envelope.

For candidate P, each allowed OCR operation has three short transactions (A admission, B final dispatch, C settlement), plus existing authentication lookups and amortized recovery/cleanup. A denied request has at most A and no B/C; pre-auth/input/config failure can stop earlier. No DB connection is retained during provider HTTP. With a definer-function implementation, each transaction can use BEGIN + one feature function + COMMIT (roughly 3 round trips plus bounded pool setup); application-level authority helpers add roughly 8–12 SQL statements to A/B unless safely composed into the function. Expected total is approximately 9–35 DB round trips per allowed request depending on accepted function/authorization composition; instrument the actual implementation before claiming a figure.

Let request rate be r/s, average total DB-held time h seconds across A+B+C, and provider time p seconds. Expected average OCR DB occupancy is r×h (Little's law), while local/remote in-flight pressure is approximately r×p, subject to approved caps. Example h=0.03s, r=5/s gives 0.15 DB connections on average; p=4s gives demand of 20 in-flight calls. These assumed times are not repository measurements or acceptable production limits by themselves. Tail lock waits, pool setup, bursts and non-OCR work dominate sizing.

| Workload                | Planning implication                                                            | Required benchmark                                                                           |
| ----------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| One API                 | Shared state still required for restart safety                                  | Baseline A/B/C latency, memory, rows and mock fetch count                                    |
| Two APIs                | Limits apply to combined traffic, not 2× allocation                             | Same total load then split evenly; aggregate database/provider oracle                        |
| Multiple tenants        | Shared global row serializes otherwise separate tenants                         | 2/10/50 synthetic tenants at approved aggregate cap; no starvation claim without measurement |
| Busy Location           | Identity bound prevents one member overlap, tenant cap bounds many members      | Same tenant many memberships plus a low-volume tenant; measure denial distribution           |
| Burst                   | Lock queue must remain finite; deny promptly without long request backlog       | 100 simultaneous synthetic requests with tiny quota/caps; lock wait/zero overshoot           |
| Slow provider           | No DB connection held while waiting; uncertain capacity can reduce availability | 100ms/4s/10s and beyond-deadline responses; pool usage independent of provider wait          |
| Provider outage         | Error traffic must not create unlimited paid retries or stored denied rows      | 429/5xx/timeout storm at admitted cap; DB and Native fallback latency                        |
| DB pressure             | OCR must not starve custody/auth/Guest connections                              | Mixed representative traffic; bounded queue/waiter/rejection and pool capacity envelope      |
| Hot global row          | Serial throughput upper bound about 1/critical-section-time                     | Measure critical section at 1/2/4 processes; no sharding that loses global cap               |
| Cleanup/network failure | Batch work and retry attempts compete for connections                           | Backlog + DB disconnect + API restart; no unbounded timer overlap                            |

Storage example: assume 100,000 admitted requests/day, one reservation, two rate events and about three usage facts each => roughly 600,000 rows/day. At an assumed 0.5–1.5 KiB total indexed footprint per admitted request this is roughly 50–150 MiB/day, before WAL/backups/bloat; real row width/index count must be measured. If six rows actually average 0.5 KiB each, footprint is about 300 MiB/day, illustrating sensitivity. Global/tenant caps bound admitted growth; denied attempts must not write one durable event per request. Retention/archival capacity is U-008, not an invented compliance period.

Proposed acceptance: at approved launch traffic, additional admission+dispatch DB latency p95 <=100ms and p99 <=250ms, no unbounded lock waits, no capacity/quota overshoot, no external HTTP under a DB lease, and all attempts terminate within approved request/DB/provider deadlines. Combined latency must fit the Native 15-second timeout with network margin; provider max 10 seconds does not leave room for arbitrary multi-second A/B/C waits. Require custody/Guest p95 degradation <=10% at steady approved load, no exhaustion of reserved DB connections, bounded cleanup lag and no low-volume tenant blocked solely by another tenant's allocation consumption while global capacity remains. These targets and fairness definition remain U-011.

Measure one/two/more actual processes, record hardware/PG version, dataset, build SHA, exact nonsecret config, workload timestamps, warmup/duration, p50/p95/p99, lock waits, DB acquisition/CPU/memory/WAL, storage and provider mock receive intervals. Benchmark success never substitutes for security or hard-crash proof.

## 27. Rollback and Failure Recovery

IF P is accepted, the first mitigation is shared platform OFF, then tenant OFF where appropriate. Verify every API/worker consumes shared control at its next dispatch gate. Local abort is best effort. Fence old send-capable processes and retain provider/account safeguards during drain; a deployment restart alone cannot prove old remote work stopped.

Application rollback to today's release restores unconditional production denial; it must not attempt to convert new reservations into old memory entries. Retain the new tables/functions and immutable accounting. Continue compatible restricted reconciliation until SEND_POSSIBLE/REMOTE_UNKNOWN are resolved; do not delete rows or reset quotas to “unlock” OCR. Denial is preferable to unaccounted paid retries.

Database outage before admission denies. During settlement, durable debit survives; on recovery inspect state using the owned/internal capability and converge one terminal observation, not another outbound call. Never replay HTTP because an SQL transaction or API response was lost.

Backup restore is a cost-control hazard: restoring to a point before paid sends can erase debits and allow spending twice. Keep OCR OFF across restore/failover with suspected lost commits, fence all old processes, compare restore watermark with independent vendor/account and retained external release evidence, and conservatively carry or exhaust the uncertain budget. Restore acceptance must prove no stale snapshot can silently re-enable a fresh allowance. PostgreSQL durability/failover topology is deployment evidence, not guaranteed by use of SQL.

No automatic schema down migration is promised. New enums/tables/history may be irreversible in practical operation. Any later schema removal is a reviewed forward migration after both compatibility and retention evidence. Limit changes are prospective; rollback of a configuration revision cannot roll back vendor billing or erase original history.

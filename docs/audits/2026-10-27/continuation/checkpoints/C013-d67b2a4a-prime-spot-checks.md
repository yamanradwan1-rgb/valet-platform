## Cross-check of historical high-priority finding (not new C013 file credit)

- SEC-011 / Issue #363 remains `HIGH_CONFIDENCE_SOURCE`, P1 candidate, subject to isolated runtime validation. `mfa-recovery.service.ts:61–141` requires a valid staff session, rate limit, user/factor lock and a matching unconsumed recovery code, then retires the active factor and creates a pending TOTP factor for the **user**. `mfa-enrollment.service.ts:60–91` returns the pending factor's decrypted provisioning secret to any separately valid session for the same user after eligibility checks, without binding that read to the initiating recovery session. `mfa-enrollment.service.ts:93–168` accepts confirmation for that user's pending factor with its current TOTP. Thus a pre-existing second same-user bearer session is a realistic prerequisite for provisioning-secret disclosure during the recovery window; this is not a cross-tenant or unauthenticated attack and no HTTP/PostgreSQL exploitation test was performed. Existing locks, recovery-code verification, audit events and rate limits mitigate some paths but do not visibly establish recovery-session ownership on the pending secret read.

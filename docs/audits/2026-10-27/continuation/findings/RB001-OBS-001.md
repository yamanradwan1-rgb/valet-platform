# RB001-OBS-001 — HTTP_METRIC format/label-cardinality contract drift

Provisional severity: **P2 operational/monitoring compatibility**. Confirmed static source and documentation mismatch; no production ingestion/parser failure demonstrated. Reviewed against main `2c181fc3a92808ebd0834b6d2e4f66ccc2c588a8`.

## Source and contract

- `apps/api/src/common/observability/http-metrics.middleware.ts:35-49` appends route-specific diagnostics to the existing `HTTP_METRIC` log record on selected staff routes.
- `apps/api/src/common/observability/performance-request-diagnostics.ts:66-88` appends `route`, `requestId`, `errorCode` and `reason`. The route/error classifications are bounded and fixed, but the requestId is a per-request potentially high-cardinality value.
- `apps/api/src/common/http/api-request.ts:13-19` restricts requestId lexical form and length; it does not convert IDs into low-cardinality metric labels. This is acceptable for correlation logs, not for metrics labels.
- `infra/monitoring/README.md:10-25` and `infra/monitoring/guest-t4-alert-policy.json:12-16` still describe HTTP_METRIC as fixed operation/outcome/status/durationMs and require fixed-field projection rules, with no documented treatment for the appended requestId.
- `apps/api/test/performance-request-diagnostics.test.ts:63-68` expects the suffix but does not test an external parser or high-cardinality label projection.

## Impact and limits

Fixed-field log parsers, especially anchored formats, may reject suffixed records; generic tag extraction may accidentally promote high-cardinality requestId into metric labels. **Neither effect is confirmed in production.** The monitoring directory explicitly states provider ingestion and alert delivery are not configured/deployed, so this is not a current live availability P1. Raw URL/query, location selector, authorization token and driver/SQL message are not appended. The existing operation observer already logs sanitized requestId on another stream; this is an observability compatibility issue, not a newly proven cross-tenant information disclosure.

## Suggested eventual remediation (not authorized in this audit)

Document and test the exact log-to-metric projection schema, explicitly drop requestId from metric labels (retain only in bounded correlation logs), and add parser-contract tests for both ordinary and extended staff records. Alternatively emit separate `PERFORMANCE_REQUEST` diagnostic lines with a distinct parser contract. Validate ingestion in approved staging before claiming alert readiness.

No product edit, monitoring provider configuration, issue creation, external test, or deployment performed. This finding remains a source-level P2 candidate pending operational integration validation.

## 5. DERIVED conclusions

- Duplicated **test scaffolding** or a shared assertion literal is a potential maintainability issue; it is not evidence that one operational path may go untested. A shared runner should still instantiate both endpoint cases (A01/A02).
- Independent fresh/upgrade fixtures explain why removing two simple migration-count assertions alone would have negligible expected runtime impact. Whether fixtures can safely be shared or suites rescheduled is **unmeasured** (D03/D05).
- The second negative comparison to an invented Dashboard route swap follows logically from a stronger equality check in the same source (`apps/dashboard/src/features/help/context-help-coverage.test.ts:73-76,98-106`). A future deletion of only that tautology is a plausible REMOVE candidate (U03), pending regression verification.

## 7. Risks / boundary violations

- **Critical:** removing only one of two different HTTP endpoint guards creates an authorization/IDOR blind spot even if its response code currently matches. Merging test *definitions* must retain both executions.
- **Critical:** deleting a similarly titled FK, custody or concurrency test can silently remove a different database table, lifecycle stage, or terminal-state protection (A04-A06, D04).
- **Significant:** changing DB fixtures or scheduling browser coverage without measured equivalence weakens upgrade assurance or real-user interaction coverage (D05, U02/U05).
- **Significant:** changing test inventories to fit current counts mechanically can mask an unexpected migration, route or help surface; do not loosen expectations to make a suite pass (D01/D03, U03/U04).

**A01 — MERGE: seven HTTP auth guard cases.** Sources: `apps/api/test/staff-check-in-drafts-auth.integration.test.ts:20-109` and `apps/api/test/staff-check-in-continuations-auth.integration.test.ts:20-109`; individual starts align at `:21`, `:30`, `:41`, `:56`, `:69`, `:84`, `:99`. All proposals concern tests/fixtures or runner cadence, not new product mutations. Existing command concurrency and replay assertions in A04-A06 remain required, including first execution, identical retry, concurrent identical execution, conflicting concurrent execution, retry after success, and the loser result. On an uncommitted or rolled-back transaction, the winner must not be inferred from an API timeout; tests must confirm durable state and audit after rollback/unknown caller outcome. For assignment and eligibility, a previously successful read cannot justify a later mutation after concurrent revocation/reassignment: preserve the check-use invalidation and accepted consumer transaction/guard at the point of the write. These are conditions for *retaining* existing protections, not proposals for new business behavior. This documentation change creates no additional protected mutation or audit event.
